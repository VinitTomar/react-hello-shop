# v0.7 — Context API

### Product Requirement Specification

---

## 1. Overview

**Goal:** Add two application-wide state concerns — authentication and theme — using the React Context API. Each concern gets its own typed context, provider, and consumer hook. The app gains a working dark/light mode toggle that persists to `localStorage` and a mock auth flow (login / logout) that displays the user's name in the Header.

**End result:** The Header shows a theme toggle button (☾ / ☀) and a "Log in" button. Clicking "Log in" displays the username and a "Log out" button. Clicking ☾ switches the full UI to dark mode; the preference survives page reloads. All existing pages and components adapt their colours via Tailwind `dark:` utility classes — no white text on white backgrounds, no invisible elements.

**Why this comes after v0.3:** Context requires a component tree to provide context into, and navigation (`useNavigate`, `useParams`) must already work so the Header can link to `/cart`. v0.7 is deliberately placed after v0.3 and is independent of v0.4 (Forms), v0.5 (Custom Hooks), and v0.6 (Zustand) — all of those use local or server state, not global tree state.

### Tailwind CSS v4 — Dark Mode Is Different

This project uses **Tailwind CSS v4**, which does not use `tailwind.config.js`. Class-based dark mode in v4 requires a single CSS directive:

```css
@custom-variant dark (&:where(.dark, .dark *));
```

This replaces the v3 `darkMode: 'class'` config key. Once added to `index.css`, any `dark:` utility class activates when an ancestor has the `dark` class. `ThemeContext` adds/removes `dark` on `document.documentElement`.

### Module Constraints

- **Mock auth only.** The "Log in" button fires `login()` with a hardcoded user object — no form, no HTTP, no tokens. The context pattern is the lesson; real auth is v0.8+.
- **No new packages.** Context is built into React. No install step.
- **Context splitting is required.** Auth and Theme must be separate concerns — never combined into one context or provider.
- **`createContext(null)` pattern.** Both contexts use `null` as the default value and throw a descriptive error in their custom hook if called outside the provider. This is the only pattern used — do not use `createContext({} as T)` or `createContext(undefined as unknown as T)`.
- **Three-file split per context.** The `react-refresh/only-export-components` ESLint rule does not allow mixing a `createContext()` export and a component export in the same `.tsx` file. The fix: `.ts` files are not scanned by the rule, so context objects live in `.ts` files; providers live in `.tsx` files; hooks live in `src/hooks/`. Each file exports exactly one kind of thing.
- **File naming convention:** `authContext.ts` / `themeContext.ts` (camelCase — no JSX, not scanned) for context objects; `AuthProvider.tsx` / `ThemeProvider.tsx` (PascalCase — component file) for providers.
- **Providers in `main.tsx`.** Following the pattern set for `<BrowserRouter>` in v0.3, application-level providers are composed in `main.tsx`, not nested inside `App.tsx`.
- **Flash of wrong theme on first load.** `useEffect` runs after the first render, so if dark mode was stored, there is a brief flash. The production fix (inline `<script>` in `index.html`) is out of scope. The spec acknowledges this limitation explicitly.
- **Tailwind only.** No inline styles, no CSS modules.

### 5.1 `src/index.css` — UPDATED

**Requirements:**

- Add `@custom-variant dark (&:where(.dark, .dark *));` as the second line, immediately after `@import "tailwindcss"`
- Keep the existing `body { @apply bg-gray-50; }` rule — do not add a dark variant here (the `<main>` element owns the page background for dark mode)
- No other changes

```css
@import "tailwindcss";
@custom-variant dark (&:where(.dark, .dark *));

body {
  @apply bg-gray-50;
}
```

> **Why `(&:where(.dark, .dark *))`:** This selector matches any element that is `.dark` itself or is a descendant of `.dark`. Adding `dark` to `<html>` means the entire document matches, activating all `dark:` variants. The `:where()` wrapper has zero specificity, so component-level overrides remain easy.

### 5.3 `src/context/authContext.ts` — NEW

**Requirements:**

- `.ts` extension — no JSX, so the `react-refresh/only-export-components` rule does not scan this file
- Named exports: `AuthContextValue` interface, `AuthContext` context object
- `AuthContext` is exported so `AuthProvider.tsx` and `useAuth.ts` can import it
- No `any` types

> **Why `createContext(null)` not `createContext({} as AuthContextValue)`:** The `null` default makes it possible to detect a missing provider at runtime. A non-null default would silently return a broken object with no-op functions and `user: undefined`, making bugs invisible. The `null` guard in `useAuth` converts the detection into a clear, actionable error message.

> **Why `AuthContext` is exported:** `AuthProvider.tsx` needs it to render `<AuthContext.Provider>`, and `useAuth.ts` needs it for `useContext(AuthContext)`. Exporting it from a `.ts` file is safe — app code must still call `useAuth()`, not `useContext(AuthContext)` directly.

### 5.4.1 `src/context/ThemeProvider.tsx` — NEW

**Requirements:**

- Named export: `ThemeProvider` component only
- Imports `ThemeContext` and `Theme` from `@/context/themeContext`
- Uses `useLocalStorage<Theme>("theme", "light")` from `@/hooks/useLocalStorage` for persistence — do not call `localStorage` directly
- Applies/removes `dark` class on `document.documentElement` in a `useEffect` that depends on `theme`
- `toggleTheme` calls the `useLocalStorage` setter with the toggled value directly (not a functional update — the setter doesn't accept `(prev) => next`)

> **Why `useLocalStorage` instead of raw `localStorage`:** `useLocalStorage` (built in v0.5) already handles the lazy initializer pattern and write-on-change. Reusing it here demonstrates hook composition — a hook calling another hook — and keeps `ThemeProvider` focused solely on the DOM side effect.

> **Why `useEffect` for classList:** Adding a class to `document.documentElement` is an imperative DOM side effect. React's render phase must be pure. The effect runs synchronously after the first paint, which causes a brief flash on first load if dark mode was stored. The fix — a `<script>` tag in `index.html` that sets the class before React hydrates — is a production concern outside the scope of this module.

### 5.5 `src/main.tsx` — UPDATED

**Requirements:**

- Import `ThemeProvider` from `@/context/ThemeContext`
- Import `AuthProvider` from `@/context/AuthContext`
- Wrap `<App />` with both providers, inside `<BrowserRouter>`, in this order (outermost first): `ThemeProvider` → `AuthProvider` → `App`
- `<StrictMode>` remains the outermost wrapper

**Provider tree:**

```
<StrictMode>
  <BrowserRouter>          ← from v0.3
    <ThemeProvider>        ← NEW (outer: theme is more global than auth)
      <AuthProvider>       ← NEW (inner: auth could consume theme in future)
        <App />
      </AuthProvider>
    </ThemeProvider>
  </BrowserRouter>
</StrictMode>
```

> **Order rationale:** `ThemeProvider` is outer because it has no dependency on `AuthContext`. If a future provider needed to consume `ThemeContext` (e.g. a logging provider that records theme preference), it could because `ThemeProvider` is already above it. Inner providers can consume outer context; the reverse is not possible.

## 7. Concepts Learned

| Concept                            | Where it appears                    | Why it matters                                                                                                                                                                                                                |
| ---------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createContext<T \| null>(null)`   | `authContext.ts`, `themeContext.ts` | The `null` default makes "used outside provider" detectable; a non-null default hides the bug                                                                                                                                 |
| Runtime guard in hook              | `useAuth`, `useTheme`               | The guard converts `null` into a clear error message; the return type narrows from `T \| null` to `T` so callers never null-check                                                                                             |
| Provider composition order         | `main.tsx`                          | Outer providers can be consumed by inner providers but not vice versa — place the most global provider outermost                                                                                                              |
| Splitting contexts                 | Auth vs Theme are separate files    | A single combined context would re-render all consumers on every auth or theme change; separate contexts scope re-renders to only interested components                                                                       |
| `.ts` vs `.tsx` file roles         | All context files                   | The `react-refresh/only-export-components` rule only scans `.tsx` files. Context objects and hooks (no JSX) go in `.ts`; Provider components (JSX) go in `.tsx`. This keeps each `.tsx` file exporting exactly one component. |
| `ReactNode` children type          | Both providers                      | The correct type for any renderable JSX tree passed to a wrapper component                                                                                                                                                    |
| Hook composition                   | `ThemeProvider`                     | `ThemeProvider` calls `useLocalStorage` — a hook calling another hook. Each hook handles one concern: `useLocalStorage` owns persistence, `ThemeProvider` owns the DOM class toggle.                                          |
| `useEffect` for DOM side effects   | `ThemeProvider`                     | Toggling a CSS class on `<html>` is an imperative mutation outside React's tree — it must live in `useEffect`, not in render                                                                                                  |
| Tailwind v4 `@custom-variant dark` | `index.css`                         | Replaces the v3 `tailwind.config.js` `darkMode: 'class'` key — Tailwind v4 is CSS-native, configuration lives in the stylesheet                                                                                               |
| `dark:` utility classes            | All updated files                   | Each token is expressed as one class pair (`text-gray-900 dark:text-white`) — no conditional className logic in JSX                                                                                                           |
