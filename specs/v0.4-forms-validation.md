# v0.4 — Forms & Validation

### Product Requirement Specification

---

## 1. Overview

**Goal:** Add a live-filtering search bar and filter sidebar to the Home page using React Hook Form and Zod. Users can narrow the product grid by name (text search), category (checkbox group), and price range (min/max inputs) — all simultaneously, all without a submit button.

**End result:** The Home page renders a search input above a two-panel layout: a filter sidebar on the left and the product grid on the right. Every keystroke or checkbox change immediately updates the visible products. Entering an invalid price range (min > max) shows an inline validation error on the max input. The product grid's existing empty-state message appears when no products match. All other pages and routes are untouched.

**Why this comes after v0.3:** Forms are the primary way users send data to an application. Before building forms, route-level navigation must exist so each page can own its own form state without prop-drilling through `App.tsx`. v0.4 deliberately keeps filtering client-side (no API, no URL state) so the learning focus stays on form wiring and validation, not data fetching or routing concerns.

### Module Constraints

- **Client-side filtering only.** No API calls, no debounce, no pagination — 6 products, filtering is instant.
- **Live filtering via `watch()`.** No submit button. Filters apply on every change event.
- **No URL state.** Filters are not synced to the URL — navigating away and back resets them. URL-synced filters are a future module.
- **Categories hardcoded.** `CATEGORIES` is a `const` array in the schema — not derived from `MOCK_PRODUCTS` at runtime. Dynamic derivation with `useMemo` is a v0.5 pattern.
- **`useForm` lives in `Home.tsx`.** Child components receive `register` and `errors` as explicit props — no `FormProvider`/`useFormContext`. Explicit prop flow is clearer for learning.
- **Tailwind only.** No inline styles, no CSS modules.
- **React 19 JSX transform.** No `import React from 'react'` needed.

### Out of Scope (do not build in this module)

| Feature                                  | Planned for                      |
| ---------------------------------------- | -------------------------------- |
| Debounced search                         | v0.5 (`useDebounce` custom hook) |
| URL-synced filter state                  | future                           |
| Sort (price asc/desc, alphabetical)      | future                           |
| Pagination / infinite scroll             | v0.10                            |
| Category list derived from live API data | v0.9                             |
| Persisted filter preferences             | v0.6+                            |

### 5.1 `src/schemas/filter.ts` — NEW

No visual. Pure TypeScript/Zod module.

**Requirements:**

- Named exports: `CATEGORIES`, `Category`, `filterSchema`, `FilterValues`
- `CATEGORIES` must be `as const` — `z.enum()` requires a readonly tuple; without `as const` TypeScript infers `string[]` and the call fails at compile time
- **Zod v4 — `z.union` instead of `z.preprocess` for price fields:** RHF's `{ valueAsNumber: true }` register option produces `NaN` for empty inputs. In Zod v4, `z.preprocess` types its output as `unknown`, which conflicts with RHF's `Resolver<FilterValues>` type. The fix is `z.union([z.number().nonnegative(), z.nan().transform(() => undefined)])` — `z.nan()` matches exactly when the value is NaN and transforms it to `undefined`; valid numbers pass through the first branch; negative numbers fail the `nonnegative` check and surface as an error. This keeps the output type as `number | undefined`, which `zodResolver` infers correctly.
- `.refine` fires only when both prices are non-null numbers — safe to compare; error path is `["maxPrice"]` so it surfaces on the max input in `FilterPanel`
- `FilterValues` is inferred from the schema — never write the type by hand
- No React imports — pure TypeScript module

**Requirements:**

- Checkboxes: multiple `<input type="checkbox">` elements sharing the name `"categories"` — RHF collects their checked values into an array automatically. The `value` attribute on each input determines what gets pushed into the array.
- Price inputs: `{ valueAsNumber: true }` in the register options tells RHF to call `parseFloat(input.value)` on change, producing a `number` (or `NaN` for empty). The schema's `z.preprocess` converts `NaN → undefined`.
- Error display: the cross-field `.refine` error targets `path: ["maxPrice"]` — it appears as `errors.maxPrice.message`. Only the max input shows it.
- `minPrice` errors (e.g. negative number) would appear on the min input; add `{errors.minPrice && <p ...>{errors.minPrice.message}</p>}` below the min input if desired — the spec shows maxPrice only since that's where the cross-field error lands.
- `CATEGORIES` is imported from `@/schemas/filter` — do not re-declare the array here.

## 7. Concepts Learned

| Concept                                 | Where it appears           | Why it matters                                                                                                                                                                                                                              |
| --------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useForm<T>` with a generic             | `Home.tsx`                 | The generic anchors all field names to `FilterValues` — no `any`, no string field names at risk of typo                                                                                                                                     |
| `zodResolver`                           | `Home.tsx`                 | Bridges Zod schema to RHF validation — one schema is both the TypeScript type source and the runtime validator                                                                                                                              |
| `z.infer<typeof schema>`                | `schemas/filter.ts`        | Derives the TS type from the Zod schema — type and validation stay in sync automatically                                                                                                                                                    |
| `z.union` + `z.nan()` for NaN coercion  | `schemas/filter.ts`        | Handles `NaN` from number inputs by matching it explicitly with `z.nan()` and transforming to `undefined` — Zod v4 compatible alternative to `z.preprocess`, which types its output as `unknown` and breaks RHF's `Resolver` type inference |
| `.refine` for cross-field validation    | `schemas/filter.ts`        | Validates a relationship between two fields; `path` targets the error to a specific field's error slot                                                                                                                                      |
| `{ valueAsNumber: true }` in `register` | `FilterPanel.tsx`          | Tells RHF to cast the raw string DOM value to a number before passing to Zod — avoids string/number type mismatch                                                                                                                           |
| `watch()` for live derived state        | `Home.tsx`                 | Subscribes to the entire form's current values — correct way to derive `filteredProducts` without a submit event                                                                                                                            |
| Checkbox array in RHF                   | `FilterPanel.tsx`          | Multiple checkboxes sharing a `name` produce a string array value — RHF handles this natively when `value` is set on each input                                                                                                             |
| `as const` + `z.enum`                   | `schemas/filter.ts`        | `as const` preserves the literal tuple that `z.enum` requires; without it `string[]` causes a TS error at the `z.enum(CATEGORIES)` call                                                                                                     |
| Explicit prop API for form context      | `SearchBar`, `FilterPanel` | Passing `register` and `errors` as props keeps form state ownership clear — one `useForm` call, no hidden context                                                                                                                           |
