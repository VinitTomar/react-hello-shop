# v0.10 — Advanced Query Patterns

### Product Requirement Specification

---

## 1. Overview

**Goal:** Extend ReactMart's server-state layer with two advanced TanStack Query patterns — optimistic mutations (wishlist add/remove) and paginated infinite scroll (product listing). Extract wishlist logic into a reusable `useWishlist` hook that wraps `useQuery` + `useMutation`. Replace `useQuery` in `Home.tsx` with `useInfiniteQuery` backed by a paginated MSW handler.

**End result:** Every product card shows a heart icon button. Clicking it flips the heart immediately (optimistic), fires a POST/DELETE to MSW, and — on simulated error — reverts the icon back. The Home page loads 3 products initially; a "Load More" button appends the next 3; after all 6 are shown, the button is replaced with "You've seen all 6 products." Navigating to other pages and back preserves the accumulated product list because `useInfiniteQuery` caches all pages.

**Why this comes after v0.9:** v0.9 established the read side — `useQuery` for single resources and lists, `QueryClient`, MSW. v0.10 adds the write side (`useMutation` with optimistic updates) and an advanced accumulating-read pattern (`useInfiniteQuery`). Together they cover the full TanStack Query API surface used in production React apps.

### Module Constraints

- **MSW for all mutations.** POST and DELETE go through MSW handlers with a 300 ms simulated delay. No real server.
- **Optimistic update on every toggle.** The heart icon must flip immediately on click without waiting for the MSW response. If the handler returns an error, the icon must revert.
- **"Load More" only — no IntersectionObserver.** The infinite-scroll trigger is a button, not a scroll event. True scroll-triggered loading distracts from learning the hook; a button makes the fetch/page progression explicit.
- **Wishlist is in-memory only.** MSW's module-level `let wishlist: string[] = []` resets on page refresh — no persistence. This makes the rollback demo easy to trigger by refreshing.
- **Page size is 3.** With 6 `MOCK_PRODUCTS`, this produces exactly 2 pages: enough to demonstrate `getNextPageParam` returning `undefined` (end of data) after page 2.
- **`useWishlist` is called directly in `ProductCard`.** TanStack Query deduplicates the `GET /api/wishlist` fetch — every card calling the hook shares the same cached response. No prop drilling needed.
- **Tailwind only.** No inline styles, no CSS modules.
- **React 19 JSX transform.** `import React from 'react'` is not needed.

### Out of Scope (do not build in this module)

| Feature                                                        | Planned for                                   |
| -------------------------------------------------------------- | --------------------------------------------- |
| True scroll-triggered loading (IntersectionObserver)           | future                                        |
| Wishlist page (`/wishlist` route)                              | future                                        |
| Wishlist persistence (localStorage or server)                  | future                                        |
| Prefetching on hover (`queryClient.prefetchQuery`)             | future                                        |
| Paginated navigation with page numbers (prev / next buttons)   | never — infinite scroll is the chosen pattern |
| Error simulation UI (button that forces an MSW error response) | future                                        |
| Migrating product fetching from MSW to a real API              | v0.9 concern — not revisited here             |

## 4. API Surface & Query Keys

All endpoints are handled by MSW. This table is the full server-state contract for v0.10.

| Endpoint                       | Method | Response shape   | Query key          | MSW delay                     |
| ------------------------------ | ------ | ---------------- | ------------------ | ----------------------------- |
| `/api/products?page=n&limit=3` | GET    | `ProductPage`    | `['products']`     | 600 ms                        |
| `/api/products/:id`            | GET    | `Product`        | `['products', id]` | 400 ms (delay added in v0.10) |
| `/api/wishlist`                | GET    | `string[]`       | `['wishlist']`     | 300 ms                        |
| `/api/wishlist/:productId`     | POST   | `{ id: string }` | — (mutation)       | 300 ms                        |
| `/api/wishlist/:productId`     | DELETE | `void` (204)     | — (mutation)       | 300 ms                        |

**Query key notes:**

- `['products']` is now an `useInfiniteQuery` key. Its cache entry shape (`InfiniteData<ProductPage>`) differs from v0.9's `useQuery` shape (`Product[]`) under the same key. Because `Home.tsx` fully replaces `useQuery` with `useInfiniteQuery` in this module and `ProductDetail.tsx` uses the distinct key `['products', id]`, there is no runtime conflict.
- Both wishlist mutations call `queryClient.invalidateQueries({ queryKey: ['wishlist'] })` in `onSettled` — this refetches the wishlist regardless of whether the mutation succeeded or failed, ensuring the UI stays in sync with server truth.

### 6.2 `src/mocks/handlers.ts` — UPDATED

Two changes: replace the flat `GET /api/products` handler with a paginated one, and add three new wishlist handlers. Also add a `delay(400)` call to the existing `GET /api/products/:id` handler.

**Requirements:**

- Import `ProductPage` from `@/types/product`, `MOCK_PRODUCTS` from `@/data/products`, and `delay` from `msw` (v2 named export)
- Declare `let wishlist: string[] = []` at module level — not exported; resets on full page refresh
- All handlers are exported in the same `handlers` array as before; register `GET /api/products/:id` before `GET /api/products` so the more-specific path matches first

**`GET /api/products` (replaces the v0.9 flat handler):**

- 600 ms delay
- Read `page` (default `'1'`) and `limit` (default `'3'`) from query params; coerce both with `Number()`
- Compute `start = (page - 1) * limit`; slice `MOCK_PRODUCTS` from `start` to `start + limit`
- Respond with `{ products, hasMore, nextPage, total }` using `satisfies ProductPage` — keeps the shape in sync with the type without widening it
  - `hasMore`: `start + limit < MOCK_PRODUCTS.length`
  - `nextPage`: `page + 1` if `hasMore`, else `null`
  - `total`: `MOCK_PRODUCTS.length`

**`GET /api/products/:id` (updated — adds delay):**

- 400 ms delay (had none in v0.9)
- Find by `p.id.toString() === params.id`; return 404 with no body if not found

**`GET /api/wishlist` (new):**

- 300 ms delay; return the `wishlist` array as JSON

**`POST /api/wishlist/:productId` (new):**

- 300 ms delay; append `productId` only if not already present (idempotent); return `{ id: productId }`

**`DELETE /api/wishlist/:productId` (new):**

- 300 ms delay; filter `productId` out of `wishlist`; return 204 with no body

### 6.3 `src/hooks/useWishlist.ts` — NEW

A single hook that owns all wishlist server state: the current list, add, and remove.

**Return shape** — named export `useWishlist(): UseWishlistReturn`:

| Member           | Type                             | Description                                                    |
| ---------------- | -------------------------------- | -------------------------------------------------------------- |
| `wishlist`       | `string[]`                       | Live cache of wishlisted product IDs                           |
| `isLoading`      | `boolean`                        | `true` while the initial `GET /api/wishlist` is pending        |
| `isWishlisted`   | `(productId: string) => boolean` | Pure function — checks `wishlist.includes(productId)`          |
| `toggleWishlist` | `(productId: string) => void`    | Calls `addMutation` or `removeMutation` based on current state |

**Requirements:**

- Import `useMutation`, `useQuery`, `useQueryClient` from `@tanstack/react-query`
- `useQuery` key is `['wishlist']`; `queryFn` fetches `GET /api/wishlist`; alias `isPending` as `isLoading` and default `data` to `[]`
- `isWishlisted` is a plain function, not a hook — derived from the cached array; no `useCallback` needed

**`addMutation` — `POST /api/wishlist/:productId`:**

- `onMutate`: call `cancelQueries(['wishlist'])` first (prevents an in-flight refetch from overwriting the optimistic write), snapshot the current cache with `getQueryData`, append `productId` optimistically with `setQueryData`, return `{ previous }` as context
- `onError`: restore the snapshot via `setQueryData(['wishlist'], context?.previous)` — this is the rollback
- `onSettled`: call `invalidateQueries({ queryKey: ['wishlist'] })` regardless of success or failure — re-syncs with server truth after speculation

**`removeMutation` — `DELETE /api/wishlist/:productId`:**

- Identical `onMutate` / `onError` / `onSettled` structure as `addMutation`; `onMutate` filters `productId` out of the cached array instead of appending

**`toggleWishlist`:** calls `removeMutation.mutate` if `isWishlisted(productId)`, otherwise `addMutation.mutate`

- No `any` types

## 8. Concepts Learned

| Concept                                              | Where it appears                             | Why it matters                                                                                                                                                                   |
| ---------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useMutation`                                        | `useWishlist.ts`                             | TanStack Query's write primitive — manages the pending/success/error lifecycle for server mutations, mirroring what `useQuery` does for reads                                    |
| `onMutate`                                           | `useWishlist.ts`                             | Fires synchronously before the request — the correct place to write an optimistic update to the cache and save a snapshot for rollback                                           |
| `cancelQueries` before optimistic write              | `useWishlist.ts`                             | An in-flight background refetch arriving after your optimistic write would overwrite it; cancelling prevents this race condition                                                 |
| `onError` rollback                                   | `useWishlist.ts`                             | Receives the `context` returned by `onMutate` — restoring it undoes the speculative write; the user sees the heart revert if the server rejects                                  |
| `onSettled` + `invalidateQueries`                    | `useWishlist.ts`                             | Fires whether the mutation succeeded or failed — the "sync with reality" step that makes the cached state authoritative again after speculation                                  |
| Query deduplication                                  | `useWishlist.ts` called in `ProductCard.tsx` | Multiple components calling the same `useQuery` key share one cache entry and one in-flight request — no extra fetches for each card                                             |
| `useInfiniteQuery`                                   | `Home.tsx`                                   | A variant of `useQuery` that accumulates pages in `data.pages[]` — manages `pageParam`, `fetchNextPage`, `hasNextPage`, and `isFetchingNextPage` automatically                   |
| `initialPageParam` + `getNextPageParam`              | `Home.tsx`                                   | `initialPageParam` seeds the first request; `getNextPageParam` derives the next param from the last page's response — returning `undefined` signals the end of data              |
| `data.pages.flatMap`                                 | `Home.tsx`                                   | `useInfiniteQuery` stores pages separately, not as a flat array — `flatMap` is the canonical way to produce a flat item list for rendering                                       |
| `isFetchingNextPage` vs `isPending`                  | `Home.tsx`                                   | `isPending` = no data yet (first load skeleton); `isFetchingNextPage` = appending pages (disable Load More button) — conflating them would hide the grid during every page fetch |
| `e.stopPropagation()` on nested interactive elements | `ProductCard.tsx`                            | Prevents a button click from bubbling to the parent `<Link>` in `ProductGrid.tsx` — essential when interactive elements are embedded inside navigation wrappers                  |
