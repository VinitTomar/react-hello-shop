# v0.14 — Unit Testing

### Product Requirement Specification

---

## 1. Overview

**Goal:** Add a Vitest + React Testing Library test suite covering the three main testable units in the app: a UI component (`ProductCard`), a client-state store (`cartStore`), and a custom hook (`useDebounce`). Each target exercises a distinct testing primitive — `render` + `screen` queries, `userEvent` interactions, direct `useCartStore.getState()` assertions, and `renderHook` with fake timers. This spec also codifies existing test infrastructure and folder conventions already in place from prior modules.

**End result:** Running `pnpm test` executes all 29 tests in watch mode and they all pass (10 pre-existing hook tests + 19 new tests: 12 for `ProductCard`, 7 for `cartStore`). The test files together demonstrate how to test a component, a Zustand store, and custom hooks without duplicating production logic or mocking things that don't need mocking.

**Why this comes after v0.13:** Every file under test (`ProductCard`, `cartStore`, `useDebounce`) must be in its final implementation state before writing tests against it. v0.14 is the first module that adds no production code — only test infrastructure and test files.

### Module Constraints

- **No production code changes.** v0.14 adds only test infrastructure (`vite.config.ts` test block additions, `vitest.setup.ts`, two `tsconfig.app.json` edits — `types` and `include`, see §6.3) and new test files. No source files in `src/` are modified.
- **Test folder convention.** Tests live in a `__tests__/` subfolder within each domain (`src/components/__tests__/`, `src/hooks/__tests__/`, etc.), with filenames matching the module tested. This follows the convention established in v0.5 for hook tests.
- **Globals enabled.** `describe`, `it`, `expect`, `beforeEach`, `afterEach`, and `vi` are available in every test file without any import — configured via `globals: true` in Vitest and `"vitest/globals"` added to `types` in `tsconfig.app.json`.
- **No mocking the Zustand store.** Tests use the real store instance and reset state in `beforeEach` with `setState`. This is faster and more reliable than module mocking for stores.
- **No mocking TanStack Query.** `ProductCard` depends on `useWishlist()`, which requires a `QueryClientProvider` wrapper. Rather than mock React Query, tests provide a real but isolated `QueryClient` with `retry: false` to prevent flaky waits, and seed it via `setQueryData` where wishlist state matters. This validates the actual hook behavior while keeping the test deterministic. Stubbing `fetch` with `vi.stubGlobal` (§6.5) is not an exception to this rule — it replaces the network boundary, leaving the query, the mutation, and their callbacks running for real.
- **No snapshot tests.** Snapshots couple tests to markup details and break on cosmetic changes. All assertions target observable behavior through semantic queries.

## 5. Shared Test Patterns

These patterns appear in more than one test file.

### Query priority (prefer in this order)

| Priority | Query            | When to use                                                                |
| -------- | ---------------- | -------------------------------------------------------------------------- |
| 1st      | `getByRole`      | Buttons, headings, inputs, links — tests semantic HTML, not implementation |
| 2nd      | `getByLabelText` | Form inputs associated with a `<label>`                                    |
| 3rd      | `getByText`      | Non-interactive text content                                               |
| 4th      | `getByTestId`    | Last resort — requires adding `data-testid` to source                      |

In this module: `getByRole("button", { name: /add to cart/i })` for the cart button; `getByRole("button", { name: /add to wishlist/i })` and `/remove from wishlist/i` for the wishlist heart in its two states; `getByText("Wireless Headphones")` for product name; `getByText("$79.99")` for price.

### `queryBy*` vs `getBy*` for absence

Asserting that something is **absent** is the one case where the choice of query changes whether the test can work at all.

| Query      | On a miss                       | Use for                                                                                         |
| ---------- | ------------------------------- | ----------------------------------------------------------------------------------------------- |
| `queryBy*` | Returns `null`                  | ✓ Absence assertions — `expect(...).not.toBeInTheDocument()` receives `null` and passes cleanly |
| `getBy*`   | **Throws** before `expect` runs | ✗ Never for absence — the test reports an error, not a failed assertion                         |

Both forms _look_ correct when read quickly. The difference only shows up when the element really is missing — which is exactly the case the test exists to cover.

### `beforeEach` store reset

Reset the cart between tests with `useCartStore.setState({ items: [] })` inside `beforeEach`. Both [ProductCard.test.tsx](../src/components/__tests__/ProductCard.test.tsx) and [cartStore.test.ts](../src/store/__tests__/cartStore.test.ts) do this at file top level, so it applies to every `it` in every `describe` in the file.

Zustand's `setState` merges the provided object directly into the store state. It does not bypass `persist` — state changes still flow through the middleware and persist to storage, but they bypass the named action layer. Run in `beforeEach` (not `afterEach`) so that when a test fails, the store state remains visible for debugging in the next run.

### Mock product fixture

Each test file defines its own `mockProduct` inline — no shared fixture file. The shape must match [src/types/product.ts](../src/types/product.ts):

| Field         | Type     | Value used in both test files          |
| ------------- | -------- | -------------------------------------- |
| `id`          | `number` | `1`                                    |
| `name`        | `string` | `"Wireless Headphones"`                |
| `price`       | `number` | `79.99` — renders as `$79.99`          |
| `category`    | `string` | `"Electronics"`                        |
| `description` | `string` | `"High-quality audio."`                |
| `imageUrl`    | `string` | `"https://example.com/headphones.jpg"` |

[cartStore.test.ts](../src/store/__tests__/cartStore.test.ts) adds a second fixture, `mockProduct2` (`id: 2`, `"Cotton T-Shirt"`, `29.99`, `"Clothing"`), needed only by the test that proves `updateQuantity` is scoped to one product.

### `userEvent.setup()` pattern (v14 async API)

Three rules, applied everywhere `userEvent` appears in [ProductCard.test.tsx](../src/components/__tests__/ProductCard.test.tsx):

1. Call `userEvent.setup()` and bind the result to `user` **before** `render` — not inside the assertion.
2. Every interaction method (`click`, `type`, `keyboard`) is `async`. Always `await` it.
3. Assert only after that `await` resolves.

`userEvent.setup()` returns a bound user instance. The v14 API is more realistic than `fireEvent`: it dispatches pointer, focus, and keyboard events, not just a synthetic click.

### 6.3 `tsconfig.app.json` — UPDATED (two separate changes)

**Requires** — both target values are in §4's settings table. Implementation: [tsconfig.app.json](../tsconfig.app.json). This section carries the reasoning; §4 carries the values.

**Change 1 — `types`.** Add `"vitest/globals"` to the existing `types` array, which was `["vite/client"]` alone. This makes `describe`, `it`, `expect`, `vi`, `beforeEach`, and `afterEach` typed in every `.ts` and `.tsx` file covered by this tsconfig.

`vite/client` must stay — it types `import.meta.env`, asset imports, and other Vite-specific globals.

**Change 2 — `include`.** Add `vitest.setup.ts` alongside `"src"`, which was previously the only entry. **This is required and easy to miss.**

Why: `setupFiles` in `vite.config.ts` is a **runtime** instruction — Vitest loads the setup file when tests execute. TypeScript never reads `vite.config.ts`, so it resolves files purely from `include`. With `include: ["src"]` alone, `vitest.setup.ts` (at the repo root) belongs to **no TypeScript project at all** — [tsconfig.node.json](../tsconfig.node.json) only includes `vite.config.ts`, and the root [tsconfig.json](../tsconfig.json) is `files: []` plus references.

That matters because `@testing-library/jest-dom/vitest` works via **module augmentation** — it declares `interface Assertion` inside `declare module 'vitest'` — and a module augmentation only applies if the augmenting file is part of the program. Orphaned setup file → augmentation never loads → every `.toBeInTheDocument()` fails with `Property 'toBeInTheDocument' does not exist on type 'Assertion<HTMLElement>'. ts(2339)`.

The failure mode is deceptive: **tests pass at runtime** (Vitest loaded the setup file correctly) while the editor and `tsc --noEmit` both report errors. Adding the file to `include` puts the augmentation in the same program as the tests under `src/`, so no per-test-file `import "@testing-library/jest-dom/vitest"` is needed anywhere.

> After editing `tsconfig.app.json`, VSCode needs **TypeScript: Restart TS Server** (Cmd+Shift+P) before the squiggles clear — tsserver caches the old project graph.

### 6.4 `vitest.setup.ts` — NEW

**Requires** — a single line: a side-effect import of `@testing-library/jest-dom/vitest`, with no other content. Implementation: [vitest.setup.ts](../vitest.setup.ts).

That one import does two jobs:

1. **Runtime** — registers all `@testing-library/jest-dom` custom matchers with Vitest's `expect`. This works because the file is listed in `test.setupFiles` in `vite.config.ts`.
2. **Types** — declares the module augmentation that teaches TypeScript `.toBeInTheDocument()`, `.toHaveTextContent()`, `.toHaveClass()`, etc. exist on `expect(...)`. This works **only if the file is in `include`** — see §6.3 Change 2. Listing it in `setupFiles` alone gets you job 1 without job 2.

This file runs before every test file because it is listed in `test.setupFiles`. It does not run inside a test — it is a module-level side effect.

**Harness requirements** (file scope, outside any `describe`):

| #   | Requirement                                                                                                                                                                 | Satisfied by                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| H1  | A `renderWithClient(component, options?)` helper wraps the component in `QueryClientProvider` with a fresh `QueryClient` per call, `retry: false` and `staleTime: Infinity` | `function renderWithClient`                           |
| H2  | The helper accepts an optional `wishlist` seed and, when given, primes the cache with `queryClient.setQueryData(["wishlist"], …)` before rendering                          | the `options.wishlist` branch in the same helper      |

**Behavioural requirements** — one row per test, each naming the test that satisfies it:

| #   | Group    | Requirement                                                                                                      | Verified by                                                                            |
| --- | -------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1   | Compact  | The product name renders                                                                                         | `it("Should render the product name")`                                                 |
| 2   | Compact  | The price renders formatted to two decimal places                                                                | `it("should render price formatted to two decimal places")`                            |
| 3   | Compact  | The category badge is **absent** — it is gated on the `full` variant                                             | `it("does not render the category badge")`                                             |
| 4   | Compact  | The description is **absent** — also `full`-gated                                                                | `it("does not render the description")`                                                |
| 5   | Compact  | An "Add to Cart" button is present, findable by accessible name alone (no `data-testid`)                         | `it("renders the 'Add to Cart' button")`                                               |
| 6   | Compact  | Clicking "Add to Cart" puts exactly one item in the store with the right `product.id` and `quantity: 1`          | `it("adds the product to the cart when 'Add to Cart' is clicked")`                     |
| 7   | Full     | The category badge renders                                                                                       | `it("renders the category badge")`                                                     |
| 8   | Full     | The description renders                                                                                          | `it("renders the description")`                                                        |

| 12  | Wishlist | Clicking the heart applies `onMutate`'s optimistic write, flipping the label while the mutation is still pending | `it("optimistically marks the product as wishlisted while the mutation is in flight")` |

Rows 10–12 are what make the `QueryClientProvider` more than scaffolding. Rendering under a provider only proves the component does not throw; these three drive `useWishlist()` through its real read path and its real optimistic-write path.

**What is NOT tested:**

- The `memo` wrapping — it is an implementation detail invisible to `render()`
- Image `src` or `alt` attributes — those are structural, not behavioral
- CSS classes — those are visual details; test behavior, not styling
- Real wishlist network calls, the `onError` rollback, and `onSettled` invalidation — these need a request-mocking layer (v0.15, see the note below)

**Prerequisites at test time:**

- `ProductCard` has an "Add to Cart" `<button>` (compact variant only) and a wishlist toggle
- `useCartStore` is a real Zustand store — no mock needed; direct `setState` reset handles isolation
- `useWishlist` calls `useQueryClient()` unconditionally, so a plain `render()` with no `QueryClientProvider` in the tree throws — H1 is what prevents that

**Notes:**

- Tests that care about wishlist state **seed the cache** via `queryClient.setQueryData(["wishlist"], [...])` rather than letting the query fetch. This drives `useWishlist()` through its real code path with zero network involvement, and it is deterministic.

- **Why seeding rather than fetching.** In an unseeded render, the `/api/wishlist` query does not merely fail to find a mock — it never issues a request at all. jsdom does not provide `fetch`, so the call lands on Node's global `fetch` (undici), which rejects **relative** URLs outright: the query settles into `status: "error"` with the message `Failed to parse URL from /api/wishlist`. The rejection happens during URL parsing, before any network layer runs. Note that this is **not** a missing base URL: Vitest's jsdom environment already sets `location` to `http://localhost:3000/`, and undici does not consult `location`. Adding `environmentOptions: { jsdom: { url: ... } }` changes nothing here — verified, the error is unchanged.

  So in v0.14, with no interceptor installed, there is no way to let this query succeed. Seeding the cache sidesteps the network entirely and keeps the test deterministic.

- **What changes in v0.15.** Installing MSW's `setupServer` **does** fix relative URLs — its interceptor resolves them against `location` before the request is constructed. Verified against the installed `msw@2.15.0`: with a `http.get("/api/wishlist", ...)` handler registered, a bare `fetch("/api/wishlist")` returns the mocked payload. Once that lands, these wishlist tests can be rewritten to drive the real fetch path, and the `onError` rollback and `onSettled` invalidation become testable too.

- `vi.stubGlobal("fetch", ...)` in the optimistic-update test replaces the **network boundary**, not React Query — the mutation, its `onMutate` optimistic write, and the component all run for real. A promise that never settles pins the mutation in its pending state so the optimistic label is stable at assertion time. The stub is load-bearing, not decorative: remove it and the test fails **10 times out of 10**, because the real `fetch` rejects immediately and `onError` restores the pre-mutation label long before the assertion runs. That is a deterministic loss, not a flaky race. `vi.unstubAllGlobals()` in `afterEach` prevents the stub leaking into later tests.
- `useCartStore.getState()` reads the current Zustand state snapshot outside of a React component. No hook rules apply — Zustand stores are plain JavaScript closures.
- The `beforeEach` reset runs before every `it` block in all three `describe` groups because it is declared at the top level of the file, not inside a specific `describe`. The same is true of the `afterEach` that clears global stubs.
- `getByRole("button", { name: /add to cart/i })` uses a regex so it matches "Add to Cart", "add to cart", or any capitalisation. If the button label changes, this test fails — intentional.

### 6.6 `src/store/__tests__/cartStore.test.ts` — NEW

**Requires** — 7 tests in a single `describe("cartStore")` group, covering initial state plus all four store actions. Implementation: [cartStore.test.ts](../src/store/__tests__/cartStore.test.ts).

**No React involved.** Pure TypeScript — no `render`, no `screen`, no JSX. All assertions call `useCartStore.getState()` directly. The same top-level `beforeEach` reset described in §5 applies here.

| #   | Requirement                                                                                             | Verified by                                                      |
| --- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | The cart starts empty                                                                                   | `it("starts with an empty cart")`                                |
| 2   | `addToCart` on a new product appends one item at `quantity: 1`                                          | `it("adds a product with quantity 1")`                           |
| 3   | `addToCart` on a product already in the cart increments its quantity instead of appending a second item | `it("increments quantity when the same product is added twice")` |
| 4   | `removeFromCart` deletes the item matching the given `productId`                                        | `it("removes a product by id")`                                  |
| 5   | `updateQuantity` sets the quantity of the targeted item                                                 | `it("updates the quantity of an item")`                          |
| 6   | `updateQuantity` is scoped by `productId` — other items in the cart keep their quantity                 | `it("does not affect other items when updating quantity")`       |
| 7   | `clearCart` empties the cart regardless of how many items it held                                       | `it("clears all items from the cart")`                           |

Requirement 6 is the one that would catch a broad mutation: it needs two products in the cart, so it uses the `mockProduct2` fixture from §5.

**Notes:**

- Calling `getState()` twice in sequence (once for `add`, once for the assertion) is intentional — each call returns the live current state. Zustand state is synchronous; no `await` needed.
- `persist` middleware writes to `localStorage` on state changes. In jsdom, `localStorage` is available but ephemeral — it resets per test file. The `setState` reset in `beforeEach` is a belt-and-suspenders measure.

## 8. Concepts Learned

| Concept                              | Where it appears                            | Why it matters                                                                                                 |
