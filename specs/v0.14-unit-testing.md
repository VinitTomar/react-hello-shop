# v0.14 — Unit Testing

### Product Requirement Specification

---

## 1. Overview

**Goal:** Add a Vitest + React Testing Library test suite covering the three main testable units in the app: a UI component (`ProductCard`), a client-state store (`cartStore`), and a custom hook (`useDebounce`). Each target exercises a distinct testing primitive — `render` + `screen` queries, `userEvent` interactions, direct `useCartStore.getState()` assertions, and `renderHook` with fake timers. This spec also codifies existing test infrastructure and folder conventions already in place from prior modules.

**End result:** Running `pnpm test` executes all 25 tests in watch mode and they all pass (10 pre-existing hook tests + 15 new tests for `ProductCard`, `cartStore`, and optional hook extras). The test files together demonstrate how to test a component, a Zustand store, and custom hooks without duplicating production logic or mocking things that don't need mocking.

**Why this comes after v0.13:** Every file under test (`ProductCard`, `cartStore`, `useDebounce`) must be in its final implementation state before writing tests against it. v0.14 is the first module that adds no production code — only test infrastructure and test files.

### Module Constraints

- **No production code changes.** v0.14 adds only test infrastructure (`vite.config.ts` test block additions, `vitest.setup.ts`, `tsconfig.app.json` one-line diff, `package.json` scripts) and new test files. No source files in `src/` are modified.
- **Test folder convention.** Tests live in a `__tests__/` subfolder within each domain (`src/components/__tests__/`, `src/hooks/__tests__/`, etc.), with filenames matching the module tested. This follows the convention established in v0.5 for hook tests.
- **Globals enabled.** `describe`, `it`, `expect`, `beforeEach`, `afterEach`, and `vi` are available in every test file without any import — configured via `globals: true` in Vitest and `"vitest/globals"` added to `types` in `tsconfig.app.json`.
- **No mocking the Zustand store.** Tests use the real store instance and reset state in `beforeEach` with `setState`. This is faster and more reliable than module mocking for stores.
- **No mocking TanStack Query.** `ProductCard` depends on `useWishlist()`, which requires a `QueryClientProvider` wrapper. Rather than mock React Query, tests provide a real but isolated `QueryClient` with `retry: false` to prevent flaky waits. This validates the actual hook behavior while keeping the test deterministic.
- **No snapshot tests.** Snapshots couple tests to markup details and break on cosmetic changes. All assertions target observable behavior through semantic queries.

## 5. Shared Test Patterns

These patterns appear in more than one test file.

### Query priority (prefer in this order)

| Priority | Query | When to use |
| --- | --- | --- |
| 1st | `getByRole` | Buttons, headings, inputs, links — tests semantic HTML, not implementation |
| 2nd | `getByLabelText` | Form inputs associated with a `<label>` |
| 3rd | `getByText` | Non-interactive text content |
| 4th | `getByTestId` | Last resort — requires adding `data-testid` to source |

In this module: `getByRole("button", { name: /add to cart/i })` for the cart button; `getByText("Wireless Headphones")` for product name; `getByText("$79.99")` for price.

### `queryBy*` vs `getBy*` for absence

```ts
// ✓ Correct: queryByText returns null when element is missing — no throw
expect(screen.queryByText("Electronics")).not.toBeInTheDocument();

// ✗ Wrong: getByText throws before the expect runs — test fails with error, not assertion
expect(screen.getByText("Electronics")).not.toBeInTheDocument();
```

### `beforeEach` store reset

```ts
beforeEach(() => {
  useCartStore.setState({ items: [] });
});
```

Zustand's `setState` merges the provided object directly into the store state. It does not bypass `persist` — state changes still flow through the middleware and persist to storage, but they bypass the named action layer. Run in `beforeEach` (not `afterEach`) so that when a test fails, the store state remains visible for debugging in the next run.

### Mock product fixture

Each test file defines its own `mockProduct` inline — no shared fixture file. The shape must match `src/types/product.ts`:

```ts
const mockProduct = {
  id: 1,
  name: "Wireless Headphones",
  price: 79.99,
  category: "Electronics",
  description: "High-quality audio.",
  imageUrl: "https://example.com/headphones.jpg",
};
```

### `userEvent.setup()` pattern (v14 async API)

```tsx
it("...", async () => {
  const user = userEvent.setup(); // create instance BEFORE render
  render(<Component />);
  await user.click(screen.getByRole("button", { name: /add to cart/i }));
  // assertions after the await
});
```

`userEvent.setup()` returns a bound user instance. All interaction methods (`click`, `type`, `keyboard`) are `async` — always `await` them. The v14 API is more realistic: it dispatches pointer, focus, and keyboard events, not just a synthetic click.

### 6.5 `src/components/ProductCard.test.tsx` — NEW

**What is tested:**
- Render correctness: name, price, category badge, description — across both variants
- Variant isolation: `compact` hides badge and description, renders "Add to Cart" button; `full` shows badge + description, hides button
- Interaction: clicking "Add to Cart" updates the cart store
- TanStack Query integration: `useWishlist()` hook works with provided `QueryClient`

**What is NOT tested:**
- The `memo` wrapping — it is an implementation detail invisible to `render()`
- Image `src` or `alt` attributes — those are structural, not behavioral
- CSS classes — those are visual details; test behavior, not styling
- Wishlist API calls — fetch fails in jsdom test environment, react-query swallows the rejection

**Prerequisites at test time:**
- `ProductCard` has an "Add to Cart" `<button>` (compact variant only) and a wishlist toggle
- `useCartStore` is a real Zustand store — no mock needed; direct `setState` reset handles isolation
- `useWishlist` requires `QueryClientProvider` wrapper — provide via helper

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import ProductCard from "@/components/ProductCard";
import { useCartStore } from "@/store/cartStore";

const mockProduct = {
  id: 1,
  name: "Wireless Headphones",
  price: 79.99,
  category: "Electronics",
  description: "High-quality audio.",
  imageUrl: "https://example.com/headphones.jpg",
};

// Helper to wrap component with QueryClientProvider
// `ProductCard` depends on `useWishlist()`, which requires this provider
function renderWithClient(component: React.ReactElement) {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false }, // Prevent retries on test failures
    },
  });
  return render(
    <QueryClientProvider client={queryClient}>
      {component}
    </QueryClientProvider>,
  );
}

beforeEach(() => {
  useCartStore.setState({ items: [] });
});

describe("ProductCard — compact variant", () => {
  it("renders the product name", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    expect(screen.getByText("Wireless Headphones")).toBeInTheDocument();
  });

  it("renders price formatted to two decimal places", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    expect(screen.getByText("$79.99")).toBeInTheDocument();
  });

  it("does not render the category badge", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    expect(screen.queryByText("Electronics")).not.toBeInTheDocument();
  });

  it("does not render the description", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    expect(screen.queryByText("High-quality audio.")).not.toBeInTheDocument();
  });

  it("renders the 'Add to Cart' button", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    expect(screen.getByRole("button", { name: /add to cart/i })).toBeInTheDocument();
  });

  it("adds the product to the cart when 'Add to Cart' is clicked", async () => {
    const user = userEvent.setup();
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />);
    await user.click(screen.getByRole("button", { name: /add to cart/i }));
    const { items } = useCartStore.getState();
    expect(items).toHaveLength(1);
    expect(items[0].product.id).toBe(1);
    expect(items[0].quantity).toBe(1);
  });
});

describe("ProductCard — full variant", () => {
  it("renders the category badge", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="full" />);
    expect(screen.getByText("Electronics")).toBeInTheDocument();
  });

  it("renders the description", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="full" />);
    expect(screen.getByText("High-quality audio.")).toBeInTheDocument();
  });

  it("does not render the 'Add to Cart' button", () => {
    renderWithClient(<ProductCard product={mockProduct} variant="full" />);
    expect(screen.queryByRole("button", { name: /add to cart/i })).not.toBeInTheDocument();
  });
});
```

**CSS classes table:** Not applicable — this file has no Tailwind classes. Tests do not assert on classes.

**Notes:**
- `renderWithClient` wraps the component in `QueryClientProvider` so `useWishlist()` works. The fetch to `/api/wishlist` fails in jsdom (no MSW mock configured for tests), react-query catches the error, and `wishlist` stays `[]` — this is fine; the tests don't assert on wishlist state, only on cart operations and rendering.
- `useCartStore.getState()` reads the current Zustand state snapshot outside of a React component. No hook rules apply — Zustand stores are plain JavaScript closures.
- The `beforeEach` reset runs before every `it` block in both `describe` groups because it is declared at the top level of the file, not inside a specific `describe`.
- `getByRole("button", { name: /add to cart/i })` uses a regex so it matches "Add to Cart", "add to cart", or any capitalisation. If the button label changes, this test fails — intentional.

### 6.6 `src/store/__tests__/cartStore.test.ts` — NEW

**What is tested:** All four store actions (`addToCart`, repeated `addToCart`, `removeFromCart`, `updateQuantity`, `clearCart`) and initial state. The "does not affect other items" test verifies the action is scoped by `productId`, not a broad mutation.

**No React involved.** Pure TypeScript — no `render`, no `screen`, no JSX. All assertions call `useCartStore.getState()` directly.

```ts
import { useCartStore } from "@/store/cartStore";

const mockProduct = {
  id: 1,
  name: "Wireless Headphones",
  price: 79.99,
  category: "Electronics",
  description: "High-quality audio.",
  imageUrl: "https://example.com/headphones.jpg",
};

const mockProduct2 = {
  id: 2,
  name: "Cotton T-Shirt",
  price: 29.99,
  category: "Clothing",
  description: "Comfortable everyday wear.",
  imageUrl: "https://example.com/tshirt.jpg",
};

beforeEach(() => {
  useCartStore.setState({ items: [] });
});

describe("cartStore", () => {
  it("starts with an empty cart", () => {
    expect(useCartStore.getState().items).toHaveLength(0);
  });

  it("adds a product with quantity 1", () => {
    useCartStore.getState().addToCart(mockProduct);
    const { items } = useCartStore.getState();
    expect(items).toHaveLength(1);
    expect(items[0].quantity).toBe(1);
  });

  it("increments quantity when the same product is added twice", () => {
    useCartStore.getState().addToCart(mockProduct);
    useCartStore.getState().addToCart(mockProduct);
    const { items } = useCartStore.getState();
    expect(items).toHaveLength(1);
    expect(items[0].quantity).toBe(2);
  });

  it("removes a product by id", () => {
    useCartStore.getState().addToCart(mockProduct);
    useCartStore.getState().removeFromCart(mockProduct.id);
    expect(useCartStore.getState().items).toHaveLength(0);
  });

  it("updates the quantity of an item", () => {
    useCartStore.getState().addToCart(mockProduct);
    useCartStore.getState().updateQuantity(mockProduct.id, 5);
    expect(useCartStore.getState().items[0].quantity).toBe(5);
  });

  it("does not affect other items when updating quantity", () => {
    useCartStore.getState().addToCart(mockProduct);
    useCartStore.getState().addToCart(mockProduct2);
    useCartStore.getState().updateQuantity(mockProduct.id, 3);
    const other = useCartStore
      .getState()
      .items.find((i) => i.product.id === mockProduct2.id);
    expect(other?.quantity).toBe(1);
  });

  it("clears all items from the cart", () => {
    useCartStore.getState().addToCart(mockProduct);
    useCartStore.getState().addToCart(mockProduct2);
    useCartStore.getState().clearCart();
    expect(useCartStore.getState().items).toHaveLength(0);
  });
});
```

**Notes:**
- Calling `getState()` twice in sequence (once for `add`, once for the assertion) is intentional — each call returns the live current state. Zustand state is synchronous; no `await` needed.
- `persist` middleware writes to `localStorage` on state changes. In jsdom, `localStorage` is available but ephemeral — it resets per test file. The `setState` reset in `beforeEach` is a belt-and-suspenders measure.

## 7. Delivery Sequence

Follow this order. Infrastructure errors are easier to diagnose before test logic is in place. The first three steps are one-time setup; the hook tests (steps 4–6) already exist and should pass immediately once setup is done.

| Step | Action | Visible result |

The store tests (Step 5) require only the Zustand module and no DOM. If they fail, the issue is in the store logic or imports. Component tests (Step 6) bring in the full RTL render pipeline and QueryClient setup. This sequence isolates layers of complexity.

## 8. Concepts Learned

| Concept | Where it appears | Why it matters |
| --- | --- | --- |
| `test.environment: "jsdom"` | `vite.config.ts` | React components need a DOM — jsdom provides `document`, `window`, `localStorage` in Node.js |
| `test.globals: true` | `vite.config.ts` | Removes boilerplate `import { describe, it, expect } from "vitest"` from every test file |
| `test.setupFiles` | `vite.config.ts` | Runs once before each test file — the correct place for global matcher registration |
| `@testing-library/jest-dom` matchers | `vitest.setup.ts` | `.toBeInTheDocument()`, `.toHaveTextContent()`, `.toHaveClass()` — assertion library for DOM nodes |
| `render` + `screen` | `ProductCard.test.tsx` | `render()` mounts the component into jsdom; `screen` queries the result via semantic selectors |
| Query priority | `ProductCard.test.tsx` | `getByRole` checks semantic HTML (accessible name, ARIA role) — tests degrade gracefully with refactors |
| `getByText` vs `queryByText` | `ProductCard.test.tsx` | `getBy*` throws on miss — use for positive assertions; `queryBy*` returns `null` — use for absence assertions |
| `userEvent.setup()` v14 API | `ProductCard.test.tsx` | Creates an async user instance that fires realistic pointer + keyboard events; always `await` interactions |
| Direct store access in tests | `cartStore.test.ts` | `useCartStore.getState()` works outside React — no `renderHook` needed for pure logic |
| `useCartStore.setState()` for reset | `cartStore.test.ts`, `ProductCard.test.tsx` | Merges directly into state and triggers persistence; deterministic reset between tests |
| `QueryClientProvider` wrapper | `ProductCard.test.tsx` | Required to render `ProductCard` since it depends on `useWishlist()` — provides real client without mocking |
