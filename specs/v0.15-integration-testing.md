# v0.15 — Integration Testing + Final Feature

### Product Requirement Specification

---

## 1. Overview

**Goal:** Build a four-step checkout flow as ReactMart's capstone feature and write integration tests that drive the full path from cart to order confirmation. The checkout flow adds three new components — `ShippingForm`, `PaymentForm`, and `OrderConfirmation` — mounted inside a `Checkout` page that manages step state. A new `POST /checkout` MSW handler completes the server contract. The test file uses RTL, `userEvent`, and `vitest-axe` to simulate real user interactions, assert the UI at each step, override the MSW handler for the error path, and run automated accessibility checks.

**End result:** Clicking "Checkout" from the Cart page (when the cart has items) navigates to `/checkout`. The user sees a three-step indicator and a shipping form. After filling and submitting shipping details (RHF + Zod validates on blur), the payment form appears. Submitting valid card details fires `POST /checkout`; the MSW handler returns an order id, and the confirmation screen renders it. Clicking "Continue Shopping" clears the Zustand cart and returns to `/`. Running `pnpm test` drives this entire journey in under 500 ms without a browser. Each checkout step passes an automated axe accessibility scan.

**Why this comes after v0.14:** v0.14 establishes the Vitest + RTL configuration, the custom `renderWithProviders` helper, and unit test patterns (render, screen queries, `userEvent`, `renderHook`). v0.15 builds on that foundation for multi-component integration tests that cross routing, form validation, Zustand cart state, and an MSW-intercepted network call in one coherent scenario. The checkout feature is the appropriate capstone: it is the only part of the app that touches every layer of the stack in a single user journey.

### Module Constraints

- **No real payment processing.** Card details are format-validated only. `POST /checkout` is always MSW — no real network call leaves Node.
- **No card data persisted.** `PaymentData` exists only in the submit handler and is never stored.
- **Step state lives in `Checkout.tsx`.** No new Redux slices or Zustand stores for checkout. `shippingData` and `orderResult` are `useState` inside the page component.
- **Forward-only navigation.** No back button between steps. Users can navigate away via the browser back button (returns to the referring page).
- **Cart guard in `Checkout.tsx`.** If the cart is empty when `/checkout` is entered (direct URL, or cart cleared elsewhere), `useEffect` immediately redirects to `/cart`.
- **`/checkout` is lazy-loaded.** Follows the v0.12 pattern: `React.lazy(() => import('@/pages/Checkout'))` in `App.tsx`.
- **Tailwind only.** No inline styles, no CSS modules.

## 4. Integration Test Anatomy

### Test Scenarios

| Scenario | User actions | Key assertion |
| --- | --- | --- |
| Full happy path | Pre-load cart → render `/checkout` → fill shipping → fill payment → submit | Order id `ORD-TEST-001` visible in confirmation |
| Shipping required fields | Submit empty ShippingForm | Error messages for all five required fields |
| Postal code format | Type `abc` in Postal Code, tab away | Inline error: "Invalid postal code" |
| Payment required fields | Advance to PaymentForm, submit empty | Error messages for card number, expiry, and CVV |
| Card number format | Type `1234` in Card Number, tab away | Inline error: "Enter a 16-digit card number" |
| API error (500) | Override MSW to return 500 → complete PaymentForm | Error banner: "Something went wrong. Please try again." |
| Empty cart guard | Render `/checkout` with empty cart | ShippingForm is absent — redirected away |
| axe — shipping step | Render `/checkout` | `axe(container)` zero violations |
| axe — payment step | Advance to PaymentForm | `axe(container)` zero violations |
| axe — confirmation step | Complete order | `axe(container)` zero violations |

### MSW Handlers for v0.15

| Method | Path | Default response | Used for |
| --- | --- | --- | --- |
| `GET` | `/products` | products array (v0.9) | Unchanged |
| `GET` | `/products/:id` | single product (v0.9) | Unchanged |
| `POST` | `/checkout` | `{ orderId: 'ORD-TEST-001', total: 79.99 }` | New — checkout submission |

The fixed `orderId` value in the default handler makes integration tests deterministic — the test can assert `screen.findByText('ORD-TEST-001')` without any dynamic extraction.

### Key Testing APIs

| API | Import | Purpose in these tests |
| --- | --- | --- |
| `userEvent.setup()` | `@testing-library/user-event` | Creates a user session that simulates pointer + keyboard events in the correct sequence |
| `screen.findByRole` | `@testing-library/react` | Async query — polls until element appears; required after render because `/checkout` is lazy-loaded through Suspense |
| `screen.getByLabelText` | `@testing-library/react` | Finds inputs by their `<label>` — simultaneously tests that every field has an accessible label |
| `waitFor` | `@testing-library/react` | Retries an assertion block until it passes or times out — used after form submit to wait for validation state |
| `user.tab()` | `@testing-library/user-event` | Moves focus to the next element, triggering `blur` on the current one — fires `onBlur` validation in RHF |
| `server.use(...)` | MSW | Overrides the default handler for one test; MSW resets to defaults via `afterEach(() => server.resetHandlers())` in `setup.ts` |
| `axe` | `vitest-axe` | Runs WCAG 2.1 checks on the rendered DOM; returns a results object |
| `toHaveNoViolations` | `vitest-axe` | Vitest matcher — fails the test and prints the full axe violation report if any violations exist |

**Handlers:**

```typescript
function handleShippingSubmit(data: ShippingData) {
  setShippingData(data)
  setStep('payment')
}

async function handlePaymentSubmit(_paymentData: PaymentData) {
  setIsSubmitting(true)
  setSubmitError(null)
  try {
    const res = await fetch('/checkout', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ items, shipping: shippingData }),
    })
    if (!res.ok) throw new Error('Checkout failed')
    const result: OrderResult = await res.json()
    setOrderResult(result)
    setStep('confirmation')
  } catch {
    setSubmitError('Something went wrong. Please try again.')
  } finally {
    setIsSubmitting(false)
  }
}

function handleContinueShopping() {
  useCartStore.getState().clear()
  navigate('/')
}
```

## 8. Concepts Learned

| Concept | Where it appears | Why it matters |
| --- | --- | --- |
| Integration test vs unit test | `checkout.integration.test.tsx` | Integration tests render a real component tree and simulate a full user journey across multiple components, routing, and async state; unit tests isolate one component with mocked dependencies — both are necessary, covering different failure surfaces |
| `userEvent.setup()` vs `fireEvent` | All test cases | `userEvent` simulates the complete browser event sequence (pointerdown → mousedown → focus → keydown → input → keyup → click); `fireEvent` dispatches a single synthetic event — `userEvent` is correct for testing real user interactions |
| `findBy*` vs `getBy*` for async UI | After render and step transitions | `getBy*` throws immediately if the element is absent; `findBy*` returns a Promise and polls (default 1 s timeout) — required whenever the UI updates asynchronously, such as after Suspense resolves a lazy-loaded component |
| `waitFor` for deferred assertions | After form submit | Wraps an assertion block and retries it on every DOM mutation until it passes or the timeout expires — the idiomatic pattern for asserting that a batch of state changes has settled |
| `screen.getByLabelText` | All form field queries | Finds `<input>` by its associated `<label>` text — this simultaneously queries the field and verifies that the label/input association exists; a missing `htmlFor`/`id` pairing fails the test |
| `user.tab()` fires `onBlur` | Postal code format test | Pressing Tab moves focus away from the current input, triggering `blur` — the event that fires RHF's `onBlur` validation mode; tests that check inline errors must blur the field first |
| `server.use(...)` for error paths | API error test | Overrides the default MSW handler for one specific test without affecting others; MSW resets to the default handlers after each test via `server.resetHandlers()` in `setup.ts` |
| `axe` programmatic accessibility | Three axe test cases | Runs WCAG 2.1 checks on the rendered DOM and returns a structured report — catches missing labels, ARIA violations, and structural issues automatically, without a browser |
| `toHaveNoViolations` | Axe assertions | `vitest-axe` extends `expect` with a readable matcher that prints the complete axe violation details on failure — far more informative than asserting `violations.length === 0` |
| RHF `mode: 'onBlur'` | `ShippingForm`, `PaymentForm` | Defers validation until focus leaves a field — prevents error messages from flashing before typing finishes; in tests, `user.tab()` is the idiomatic way to trigger blur |
| `useCartStore.setState(...)` in tests | `beforeEach` | Zustand stores expose `.setState()` that can be called outside React to inject test state before rendering — cleaner than simulating the "add to cart" flow in every test that needs a pre-loaded cart |
| Cart guard with `useEffect` + `navigate` | `Checkout.tsx` | Combining a reactive condition with `useEffect` and `navigate(..., { replace: true })` is the React Router v6 pattern for route guards — `replace: true` prevents the guarded route from appearing in browser history |
