# v0.15 — Integration Testing + Final Feature

### Product Requirement Specification

---

## 1. Overview

**Goal:** Build the shared test harness that v0.14 deliberately left out, then build a four-step checkout flow as ReactMart's capstone feature and drive it end-to-end with integration tests.

The harness comes first: an MSW **Node** server (`setupServer`), a per-test handler fixture that keeps mock state from leaking between tests, a `renderWithProviders` helper that mounts the full provider stack, `vitest-axe` accessibility matchers, and V8 coverage reporting. On top of it sit three new components — `ShippingForm`, `PaymentForm`, `OrderConfirmation` — mounted inside a `Checkout` page that owns step state, plus a `POST /api/checkout` handler that completes the server contract.

**Scope — read this before starting.** This module is roughly **2× v0.14's delivery**. It contains three things that could each stand alone:

1. the test harness (§6.3–§6.9 — four new files, three existing ones extended),
2. the checkout feature (5 new files + 2 updated), and
3. ~31 new tests across 5 new test files, taking the suite from **29 → ~60**.

Items (1) and (3) exist because v0.14's §2 "Out of Scope" table explicitly deferred MSW-in-tests, `axe-core`, coverage reporting, and page tests to this module. If you want a smaller unit of work, the natural cut is after step 13 of §7 — the checkout feature and its integration tests — leaving the page tests for v0.16.

**End result:** Clicking "Checkout" from the Cart page (when the cart has items) navigates to `/checkout`. The user sees a three-step indicator and a shipping form. After filling and submitting shipping details (RHF + Zod validates on blur), the payment form appears. Submitting valid card details fires `POST /api/checkout`; the MSW handler returns an order id, and the confirmation screen renders it. Clicking "Continue Shopping" clears the Zustand cart and returns to `/`. `pnpm test:run` drives this entire journey without a browser, and each checkout step passes an automated axe scan.

**Why this comes after v0.14:** v0.14 established the Vitest + RTL configuration, jsdom, jest-dom matchers, and the unit-test patterns (`render`, `screen` queries, `userEvent`, `renderHook`). It stopped short of a request-mocking layer, which is exactly what multi-component integration tests need. v0.15 adds that layer and then uses it: the checkout flow is the only part of the app that crosses routing, form validation, Zustand cart state, and an intercepted network call in one coherent user journey.

### Module Constraints

- **All API paths are prefixed `/api`.** Every existing handler is `/api/...`; a handler registered at `/checkout` would never match the app's fetch. This applies to handlers, `server.use()` overrides, and the fetch in `Checkout.tsx`.
- **Every new component supports dark mode.** `Header`, `Cart`, `ProductDetail`, and `App` all carry `dark:` variants. Checkout must not be the one theme-broken area. §5 lists the paired classes.
- **No real payment processing.** Card details are format-validated only. `POST /api/checkout` is always MSW — no real network call leaves Node.
- **No card data persisted.** `PaymentData` exists only in the submit handler and is never stored.
- **Step state lives in `Checkout.tsx`.** No new Redux slices or Zustand stores for checkout. `shippingData` and `orderResult` are `useState` inside the page component.
- **Forward-only navigation.** No back button between steps. Users can navigate away via the browser back button.
- **Cart guard in `Checkout.tsx`.** If the cart is empty when `/checkout` is entered, `useEffect` redirects to `/cart` with `replace: true`.
- **`/checkout` is lazy-loaded**, following the v0.12 pattern already used by every other non-index route.
- **Tailwind only.** No inline styles, no CSS modules.

## 4. Integration Test Anatomy

### Test Scenarios

Ten scenarios, all implemented in §6.16. Earlier drafts listed ten here but implemented nine — the card-number-format row had no test.

| #   | Scenario                 | User actions                                                               | Key assertion                                           |
| --- | ------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------- |
| 1   | Full happy path          | Pre-load cart → render `/checkout` → fill shipping → fill payment → submit | Order id `ORD-TEST-001` visible in confirmation         |
| 2   | Shipping required fields | Submit empty ShippingForm                                                  | Error messages for all five fields                      |
| 3   | Postal code format       | Type `abc` in Postal Code, tab away                                        | Inline error: "Invalid postal code"                     |
| 4   | Payment required fields  | Advance to PaymentForm, submit empty                                       | Errors for card number, expiry, and CVV                 |
| 5   | Card number format       | Type `1234` in Card Number, tab away                                       | Inline error: "Enter a 16-digit card number"            |
| 6   | API error (500)          | Override MSW to return 500 → complete PaymentForm                          | Error banner: "Something went wrong. Please try again." |
| 7   | Empty cart guard         | Render `/checkout` with empty cart                                         | **Lands on `/cart`** — see the note below               |
| 8   | axe — shipping step      | Render `/checkout`                                                         | `axe(container)` zero violations                        |
| 9   | axe — payment step       | Advance to PaymentForm                                                     | `axe(container)` zero violations                        |
| 10  | axe — confirmation step  | Complete order                                                             | `axe(container)` zero violations                        |

**Scenario 2 asserts five messages, not four.** With every field empty, `postalCode` fails its regex, so the fifth message is `"Invalid postal code"` — not a "required" message. Assert the string the schema actually produces.

**Scenario 7 must be asynchronous.** `/checkout` is lazy-loaded, so a synchronous `expect(screen.queryByLabelText("Full Name")).toBeNull()` immediately after render passes while the Suspense fallback is still showing — it would pass identically if the guard did not exist. The test must await arrival at `/cart`, which crosses two lazy boundaries: Checkout mounts → its `useEffect` navigates → `Cart` loads.

### 6.2 `src/mocks/handlers.ts` — UPDATED

**Requires** — the six handlers in §4's table: the five existing v0.9/v0.10 routes untouched, plus a new `POST /api/checkout`. Implementation: [handlers.ts](../src/mocks/handlers.ts).

**One change: add the checkout handler.** Nothing else in this file moves — in particular, **do not add `resetWishlist()` or `seedWishlist()` here.** Test-only exports do not belong in the dev-browser mock; §6.4 gives tests their own wishlist fixture instead, and the reasoning is worth reading before you write either function.

**Requirements:**

- Import `OrderResult` from `@/types/checkout`
- Path is `/api/checkout` — every other handler is under `/api`, and `Checkout.tsx` fetches that path
- Fixed `orderId` keeps tests deterministic — no `Math.random()`, no `Date.now()`
- **`delay()` takes no argument.** Argless `delay()` resolves in ~5 ms under Node and 100–400 ms in a browser, so the dev experience stays realistic while tests pay almost nothing. A numeric `delay(300)` would wait the full 300 ms _in tests too_ — see §8
- The existing product and wishlist handlers keep their fixed numeric delays; changing them is a v0.9/v0.10 concern, not this module's. Their cost is why §6.20/§6.21 use `findBy*`
- **`let wishlist` on line 5 stays exactly as it is** — module-scoped, with no exported way to reach it. Tests shadow these three wishlist routes rather than reaching into them; see §6.4

### 6.3 `src/mocks/server.ts` — NEW

**Requires** — a single `server` export built by `setupServer(...handlers)`. Implementation: [server.ts](../src/mocks/server.ts).

**Requirements:**

- Mirrors `src/mocks/browser.ts` exactly, swapping `setupWorker` for `setupServer` and `msw/browser` for `msw/node`

### 6.4 `src/test/wishlist-handlers.ts` — NEW

**Requires** — a `wishlistHandlers(initial: string[] = [])` factory returning the three wishlist routes as an array, each closed over its own copy of `initial`. Implementation: [wishlist-handlers.ts](../src/test/wishlist-handlers.ts).

`src/mocks/handlers.ts` holds the wishlist in a module-scoped `let`. That is fine for the dev browser, where one page load means one lifetime — but a Vitest module registry is shared by every test in the file, so the array outlives each test and one test's click changes what the next one sees.

The tempting fix is to export a `resetWishlist()` from `handlers.ts` and call it in `afterEach`. **Don't.** It leaves the singleton in place and hands you a lever to poke it, which means every future stateful handler needs its own lever — `resetOrders()`, `resetProfile()` — and each one is a test-only export sitting in the module the dev browser loads.

Replace the singleton instead. A factory closes over its own array, so a fresh call _is_ a fresh state and there is nothing to reset.

**Requirements:**

- Lives in `src/test/`, not `src/mocks/` — it is consumed only by Vitest, and `src/test/**` is already excluded from coverage (§6.9)
- `server.use(...wishlistHandlers())` runs in a global `beforeEach` (§6.5), so every test starts from a fresh, empty wishlist
- **Seeding is the same call with an argument**, from inside a test: `server.use(...wishlistHandlers(['1']))`. There is no separate seed function
- **Mirror the base handlers exactly, including all three `delay(300)` calls.** The closure is the only intended difference. Faster mocks are tempting and buy nothing measurable here — the 29-test suite runs in ~1.7 s _with_ those delays live, because the tests finish before the requests resolve. More importantly, changing latency in the same step that changes state ownership gives §7 step 6 two variables to attribute a failure to instead of one. If §6.17 test 5 later proves tight (POST 300 ms + `onSettled` refetch 300 ms ≈ 600 ms against `findBy*`'s 1000 ms default), drop the `GET` delay **at step 18**, on its own, where the cause is unambiguous
- Return a plain array. `server.use()` takes handlers as separate arguments, so callers must spread it

**Why shadowing works, and why later `use()` calls still win.** `server.use()` **prepends** runtime handlers, and MSW picks the first match — so the `beforeEach` fixture takes precedence over `handlers.ts`'s versions of the same three routes, and a `server.use(...)` _inside_ a test takes precedence over the fixture. That ordering is what lets §6.17 override `POST /api/wishlist/:productId` with a 500 even though the fixture is already registered. `server.resetHandlers()` in `afterEach` drops every runtime handler and restores the base set, so nothing accumulates across tests.

**The cost, stated plainly.** Three route definitions now exist twice — once in `handlers.ts` for the dev browser, once here for tests. They can drift. The alternative that avoids the duplication is extracting the state into a `src/mocks/db.ts` that both import, but that still leaves a singleton and still puts a test-shaped `reset()` in the mock layer. Three routes with no logic beyond an array is the cheaper trade.

### 6.6 `src/test/vitest-axe.d.ts` — NEW

**Requires** — a hand-written `declare module 'vitest'` augmentation that mixes `AxeMatchers` into `Assertion` and `AsymmetricMatchersContaining`, with the type parameters spelled out below. Implementation: [vitest-axe.d.ts](../src/test/vitest-axe.d.ts).

`vitest-axe` documents `import "vitest-axe/extend-expect"` as the way to register its matcher. **That import does not compile in this project**, and the reason is worth understanding because it is the same mechanism v0.14 debugged with jest-dom.

The package's `dist/extend-expect.d.ts` declares:

```typescript
declare module "vitest" {
  interface Assertion extends AxeMatchers {}
}
```

Vitest 4 declares `interface Assertion<T>` — one type parameter, no default. Interface declaration merging requires **identical type parameters**, so merging a zero-parameter declaration with a one-parameter one fails:

```
error TS2428: All declarations of 'Assertion' must have identical type parameters.
```

`vitest.setup.ts` is inside the TypeScript program, so the augmentation _is_ loaded and `pnpm exec tsc -b` fails. Splitting the import solves it: take the matcher from `vitest-axe/matchers` (which carries no `declare module`) and write the augmentation ourselves with the right shape.

**Requirements:**

- **`Assertion<T = any>` — the `any` is load-bearing, not laziness.** `@testing-library/jest-dom/types/vitest.d.ts` is already in the program and declares `Assertion<T = any>`. Merged declarations must agree on the _default_ as well as the arity: `<T>` + `<T = any>` compiles, and so does `<T>` + `<T = unknown>`, but `<T = any>` + `<T = unknown>` does not. Since jest-dom owns `any`, this file must use `any` too. Hence the targeted eslint-disable and the §9 carve-out
- `AsymmetricMatchersContaining` takes no type parameter — again matching jest-dom
- The top-level `import type` makes this a module, which is what turns `declare module 'vitest'` into an _augmentation_ rather than a redeclaration
- Lives under `src/`, so `tsconfig.app.json`'s `include: ["src", ...]` already picks it up — no config change
- Verify with `pnpm exec tsc -b`. If TS2428 reappears, something has pulled `vitest-axe/extend-expect` back into the program; the fix is that import, not this file

## 8. Concepts Learned

| Concept                                    | Where it appears                               | Why it matters                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Integration test vs unit test              | `checkout.integration.test.tsx`                | Integration tests render a real component tree and simulate a full journey across components, routing, and async state; unit tests isolate one unit. Different failure surfaces, both necessary                                                                                                                                                                                                                                                      |
| MSW `setupServer` in Node                  | `src/mocks/server.ts`                          | Intercepts `fetch` at the request layer, so components run their real network code. It also **resolves relative URLs** — a bare `fetch("/api/checkout")` throws `Failed to parse URL` under plain undici, but MSW resolves it against `location` before the request is constructed                                                                                                                                                                   |
| Numeric vs argless MSW `delay`             | `POST /api/checkout`                           | `delay(300)` waits the full 300 ms _in tests too_ — it is not shortened. Argless `delay()` asks for a "realistic" duration, which MSW resolves to **5 ms under Node** and 100–400 ms in a browser. Argless is almost always what a handler wants                                                                                                                                                                                                     |
| A shared render helper                     | `src/test/utils.tsx`                           | One place that mirrors the app's provider tree. When a test renders under a different tree than production, it proves something about a tree that does not exist                                                                                                                                                                                                                                                                                     |
| Store factories in tests                   | `makeStore()`                                  | A module-level singleton is shared by every test in a process. Factories are how each test gets a clean slate — the Redux counterpart to `useCartStore.setState({ items: [] })`                                                                                                                                                                                                                                                                      |
| Green for the wrong reason                 | Empty-cart guard test                          | A synchronous assertion against a lazy route passes while the Suspense fallback is up, guard or no guard. Whenever a test "passes", ask what would have to break for it to fail                                                                                                                                                                                                                                                                      |
| `findBy*` vs `getBy*` for async UI         | After render and step transitions              | `getBy*` throws immediately if the element is absent; `findBy*` returns a promise and polls (1 s default) — required whenever Suspense or a request stands between render and content                                                                                                                                                                                                                                                                |
| `waitFor` for a batch of changes           | Validation-error assertions                    | Retries a whole block until it passes. Right when several messages must appear together; a single `findBy*` is better for one element                                                                                                                                                                                                                                                                                                                |
| `screen.getByLabelText`                    | Every form field query                         | Queries the field _and_ proves the `htmlFor`/`id` pairing exists. A missing label fails the test before axe ever runs                                                                                                                                                                                                                                                                                                                                |
| `user.tab()` fires `onBlur`                | Postal code and card number tests              | Tab moves focus away, firing `blur` — the event RHF's `mode: 'onBlur'` listens for. Inline-error tests must blur first                                                                                                                                                                                                                                                                                                                               |
| `server.use(...)` prepends                 | 500 tests, rollback test, the wishlist fixture | Runtime handlers go in front of the base set and MSW takes the first match, so the most recent `use()` wins. That single rule covers both jobs: a global `beforeEach` can shadow a route for the whole suite, and a test can still override that shadow                                                                                                                                                                                              |
| Test fixtures over reset functions         | `wishlistHandlers()` vs `resetWishlist()`      | `resetHandlers()` restores handler _functions_, never their closure state — so a module-scoped `let` in a mock needs _something_. Exporting a reset from the mock keeps the singleton and adds a test-only export to the module the dev browser loads; a factory deletes the shared state instead. Same move as `makeStore()`, one layer down                                                                                                        |
| axe scans a subtree, not a page            | Three axe test cases                           | Page-level rules (`page-has-heading-one`, `landmark-one-main`, `html-has-lang`, `bypass`) select `html:not(html *)`, which cannot match inside RTL's `container` — so they never fire. `region` selects `body *` and does apply; it passes because all content lives in `<header>`/`<main>`. Scanning `container` is narrower than a real page audit, and knowing _which_ rules you skipped is the difference between a green test and a green claim |
| Matcher type augmentation must match arity | `src/test/vitest-axe.d.ts`                     | `expect.extend` is runtime; making TypeScript aware needs `declare module "vitest"`. Merged declarations must agree on type parameters _and defaults_ — `<T>` + `<T = any>` compiles, `<T = any>` + `<T = unknown>` does not. A package whose augmentation predates your test runner will fail with TS2428, and the fix is to import the matcher without the augmentation and write your own                                                         |
| V8 coverage                                | `pnpm test:coverage`                           | The V8 provider reads the engine's own counters instead of instrumenting source, so it is fast and needs no Babel step. Excluding tests, mocks, and helpers keeps the number about product code                                                                                                                                                                                                                                                      |
| RHF `mode: 'onBlur'`                       | Both forms                                     | Defers validation until focus leaves a field, so errors do not flash mid-typing. In tests, `user.tab()` is how you trigger it                                                                                                                                                                                                                                                                                                                        |
| Cart guard with `useEffect` + `navigate`   | `Checkout.tsx`                                 | A reactive condition plus `navigate(..., { replace: true })` is the React Router route-guard pattern; `replace` keeps the guarded route out of history so Back does not bounce                                                                                                                                                                                                                                                                       |
