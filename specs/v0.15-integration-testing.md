# v0.15 — Integration Testing + Final Feature

### Product Requirement Specification

---

## 1. Overview

**Goal:** Build the shared test harness that v0.14 deliberately left out, then build a four-step checkout flow as ReactMart's capstone feature and drive it end-to-end with integration tests.

The harness comes first: an MSW **Node** server (`setupServer`), a per-test handler fixture that keeps mock state from leaking between tests, a `renderWithProviders` helper that mounts the full provider stack, `vitest-axe` accessibility matchers, and V8 coverage reporting. On top of it sit three new components — `ShippingForm`, `PaymentForm`, `OrderConfirmation` — mounted inside a `Checkout` page that owns step state, plus a `POST /api/checkout` handler that completes the server contract.

**Scope — read this before starting.** This module is roughly **2× v0.14's delivery**. It contains three things that could each stand alone:

1. the test harness (§6.3–§6.9 — four new files, three existing ones extended),
2. the checkout feature (5 new files + 2 updated), and
3. ~31 new tests across 5 new test files, taking the suite from **29 → ~60**.

Items (1) and (3) exist because v0.14's §2 "Out of Scope" table explicitly deferred MSW-in-tests, `axe-core`, coverage reporting, and page tests to this module. If you want a smaller unit of work, the natural cut is after step 13 of §7 — the checkout feature and its integration tests — leaving the page tests for v0.16.

**End result:** Clicking "Checkout" from the Cart page (when the cart has items) navigates to `/checkout`. The user sees a three-step indicator and a shipping form. After filling and submitting shipping details (RHF + Zod validates on blur), the payment form appears. Submitting valid card details fires `POST /api/checkout`; the MSW handler returns an order id, and the confirmation screen renders it. Clicking "Continue Shopping" clears the Zustand cart and returns to `/`. `pnpm test:run` drives this entire journey without a browser, and each checkout step passes an automated axe scan.

**Why this comes after v0.14:** v0.14 established the Vitest + RTL configuration, jsdom, jest-dom matchers, and the unit-test patterns (`render`, `screen` queries, `userEvent`, `renderHook`). It stopped short of a request-mocking layer, which is exactly what multi-component integration tests need. v0.15 adds that layer and then uses it: the checkout flow is the only part of the app that crosses routing, form validation, Zustand cart state, and an intercepted network call in one coherent user journey.

### Module Constraints

- **All API paths are prefixed `/api`.** Every existing handler is `/api/...`; a handler registered at `/checkout` would never match the app's fetch. This applies to handlers, `server.use()` overrides, and the fetch in `Checkout.tsx`.
- **Every new component supports dark mode.** `Header`, `Cart`, `ProductDetail`, and `App` all carry `dark:` variants. Checkout must not be the one theme-broken area. §5 lists the paired classes.
- **No real payment processing.** Card details are format-validated only. `POST /api/checkout` is always MSW — no real network call leaves Node.
- **No card data persisted.** `PaymentData` exists only in the submit handler and is never stored.
- **Step state lives in `Checkout.tsx`.** No new Redux slices or Zustand stores for checkout. `shippingData` and `orderResult` are `useState` inside the page component.
- **Forward-only navigation.** No back button between steps. Users can navigate away via the browser back button.
- **Cart guard in `Checkout.tsx`.** If the cart is empty when `/checkout` is entered, `useEffect` redirects to `/cart` with `replace: true`.
- **`/checkout` is lazy-loaded**, following the v0.12 pattern already used by every other non-index route.
- **Tailwind only.** No inline styles, no CSS modules.

## 4. Integration Test Anatomy

### Test Scenarios

Ten scenarios, all implemented in §6.16. Earlier drafts listed ten here but implemented nine — the card-number-format row had no test.

| # | Scenario | User actions | Key assertion |
| --- | --- | --- | --- |
| 1 | Full happy path | Pre-load cart → render `/checkout` → fill shipping → fill payment → submit | Order id `ORD-TEST-001` visible in confirmation |
| 2 | Shipping required fields | Submit empty ShippingForm | Error messages for all five fields |
| 3 | Postal code format | Type `abc` in Postal Code, tab away | Inline error: "Invalid postal code" |
| 4 | Payment required fields | Advance to PaymentForm, submit empty | Errors for card number, expiry, and CVV |
| 5 | Card number format | Type `1234` in Card Number, tab away | Inline error: "Enter a 16-digit card number" |
| 6 | API error (500) | Override MSW to return 500 → complete PaymentForm | Error banner: "Something went wrong. Please try again." |
| 7 | Empty cart guard | Render `/checkout` with empty cart | **Lands on `/cart`** — see the note below |
| 8 | axe — shipping step | Render `/checkout` | `axe(container)` zero violations |
| 9 | axe — payment step | Advance to PaymentForm | `axe(container)` zero violations |
| 10 | axe — confirmation step | Complete order | `axe(container)` zero violations |

**Scenario 2 asserts five messages, not four.** With every field empty, `postalCode` fails its regex, so the fifth message is `"Invalid postal code"` — not a "required" message. Assert the string the schema actually produces.

**Scenario 7 must be asynchronous.** `/checkout` is lazy-loaded, so a synchronous `expect(screen.queryByLabelText("Full Name")).toBeNull()` immediately after render passes while the Suspense fallback is still showing — it would pass identically if the guard did not exist. The test must await arrival at `/cart`, which crosses two lazy boundaries: Checkout mounts → its `useEffect` navigates → `Cart` loads.

### 6.2 `src/mocks/handlers.ts` — UPDATED

**One change: add the checkout handler.** Nothing else in this file moves — in particular, **do not add `resetWishlist()` or `seedWishlist()` here.** Test-only exports do not belong in the dev-browser mock; §6.4 gives tests their own wishlist fixture instead, and the reasoning is worth reading before you write either function.

The whole file after the change — the `OrderResult` import and the final handler are the only new lines:

```typescript
import { MOCK_PRODUCTS } from '@/data/products'
import type { OrderResult } from '@/types/checkout'
import type { ProductPage } from '@/types/product'
import { delay, http, HttpResponse } from 'msw'

let wishlist: string[] = []

export const handlers = [
  http.get<{ id: string }>('/api/products/:id', async ({ params }) => {
    await delay(400)
    const product = MOCK_PRODUCTS.find((p) => p.id.toString() === params.id)
    if (!product) {
      return new HttpResponse(null, { status: 404 })
    }

    return HttpResponse.json(product)
  }),

  http.get('/api/products', async ({ request }) => {
    await delay(600)
    const url = new URL(request.url)
    const page = Number(url.searchParams.get('page') ?? '1')
    const limit = Number(url.searchParams.get('limit') ?? '3')
    const start = (page - 1) * limit
    const slice = MOCK_PRODUCTS.slice(start, start + limit)
    return HttpResponse.json({
      products: slice,
      hasMore: start + limit < MOCK_PRODUCTS.length,
      nextPage: start + limit < MOCK_PRODUCTS.length ? page + 1 : null,
      total: MOCK_PRODUCTS.length,
    } satisfies ProductPage)
  }),

  http.get('/api/wishlist', async () => {
    await delay(300)
    return HttpResponse.json(wishlist)
  }),

  http.post('/api/wishlist/:productId', async ({ params }) => {
    await delay(300)
    const id = params.productId as string
    if (!wishlist.includes(id)) wishlist = [...wishlist, id]

    return HttpResponse.json({ id })
  }),

  http.delete('/api/wishlist/:productId', async ({ params }) => {
    await delay(300)
    wishlist = wishlist.filter((id) => id !== params.productId)

    return new HttpResponse(null, { status: 204 })
  }),

  // ↓ the only addition
  http.post('/api/checkout', async () => {
    await delay()
    return HttpResponse.json<OrderResult>({
      orderId: 'ORD-TEST-001',
      total: 79.99,
    })
  }),
]
```

**Requirements:**
- Import `OrderResult` from `@/types/checkout`
- Path is `/api/checkout` — every other handler is under `/api`, and `Checkout.tsx` fetches that path
- Fixed `orderId` keeps tests deterministic — no `Math.random()`, no `Date.now()`
- **`delay()` takes no argument.** Argless `delay()` resolves in ~5 ms under Node and 100–400 ms in a browser, so the dev experience stays realistic while tests pay almost nothing. A numeric `delay(300)` would wait the full 300 ms *in tests too* — see §8
- The existing product and wishlist handlers keep their fixed numeric delays; changing them is a v0.9/v0.10 concern, not this module's. Their cost is why §6.20/§6.21 use `findBy*`
- **`let wishlist` on line 5 stays exactly as it is** — module-scoped, with no exported way to reach it. Tests shadow these three wishlist routes rather than reaching into them; see §6.4

### 6.4 `src/test/wishlist-handlers.ts` — NEW

`src/mocks/handlers.ts` holds the wishlist in a module-scoped `let`. That is fine for the dev browser, where one page load means one lifetime — but a Vitest module registry is shared by every test in the file, so the array outlives each test and one test's click changes what the next one sees.

The tempting fix is to export a `resetWishlist()` from `handlers.ts` and call it in `afterEach`. **Don't.** It leaves the singleton in place and hands you a lever to poke it, which means every future stateful handler needs its own lever — `resetOrders()`, `resetProfile()` — and each one is a test-only export sitting in the module the dev browser loads.

Replace the singleton instead. A factory closes over its own array, so a fresh call *is* a fresh state and there is nothing to reset:

```typescript
import { delay, http, HttpResponse } from 'msw'

/**
 * Test-owned wishlist routes. Each call closes over its own array, so no state
 * survives between calls — this is the mock-layer counterpart to `makeStore()`.
 */
export function wishlistHandlers(initial: string[] = []) {
  let wishlist = [...initial]

  return [
    http.get('/api/wishlist', async () => {
      await delay(300)
      return HttpResponse.json(wishlist)
    }),

    http.post('/api/wishlist/:productId', async ({ params }) => {
      await delay(300)
      const id = params.productId as string
      if (!wishlist.includes(id)) wishlist = [...wishlist, id]
      return HttpResponse.json({ id })
    }),

    http.delete('/api/wishlist/:productId', async ({ params }) => {
      await delay(300)
      wishlist = wishlist.filter((id) => id !== params.productId)
      return new HttpResponse(null, { status: 204 })
    }),
  ]
}
```

**Requirements:**
- Lives in `src/test/`, not `src/mocks/` — it is consumed only by Vitest, and `src/test/**` is already excluded from coverage (§6.9)
- `server.use(...wishlistHandlers())` runs in a global `beforeEach` (§6.5), so every test starts from a fresh, empty wishlist
- **Seeding is the same call with an argument**, from inside a test: `server.use(...wishlistHandlers(['1']))`. There is no separate seed function
- **Mirror the base handlers exactly, including all three `delay(300)` calls.** The closure is the only intended difference. Faster mocks are tempting and buy nothing measurable here — the 29-test suite runs in ~1.7 s *with* those delays live, because the tests finish before the requests resolve. More importantly, changing latency in the same step that changes state ownership gives §7 step 6 two variables to attribute a failure to instead of one. If §6.17 test 5 later proves tight (POST 300 ms + `onSettled` refetch 300 ms ≈ 600 ms against `findBy*`'s 1000 ms default), drop the `GET` delay **at step 18**, on its own, where the cause is unambiguous
- Return a plain array. `server.use()` takes handlers as separate arguments, so callers must spread it

**Why shadowing works, and why later `use()` calls still win.** `server.use()` **prepends** runtime handlers, and MSW picks the first match — so the `beforeEach` fixture takes precedence over `handlers.ts`'s versions of the same three routes, and a `server.use(...)` *inside* a test takes precedence over the fixture. That ordering is what lets §6.17 override `POST /api/wishlist/:productId` with a 500 even though the fixture is already registered. `server.resetHandlers()` in `afterEach` drops every runtime handler and restores the base set, so nothing accumulates across tests.

**The cost, stated plainly.** Three route definitions now exist twice — once in `handlers.ts` for the dev browser, once here for tests. They can drift. The alternative that avoids the duplication is extracting the state into a `src/mocks/db.ts` that both import, but that still leaves a singleton and still puts a test-shaped `reset()` in the mock layer. Three routes with no logic beyond an array is the cheaper trade.

### 6.5 `vitest.setup.ts` — UPDATED

Runs once per test file, before any test. Its job grows from one line to four responsibilities: jest-dom matchers, the axe matcher, the MSW lifecycle, and cross-test state hygiene.

afterAll(() => server.close())

**Requirements:**
- The matcher is imported from **`vitest-axe/matchers`**, never `vitest-axe/extend-expect`. The latter also ships a type augmentation that does not compile against Vitest 4 — §6.6 explains and replaces it

- **The `beforeEach`/`afterEach` pair is what isolates wishlist state, and both halves are load-bearing.** `server.resetHandlers()` restores *which handlers are registered* — it cannot reach inside a closure, so it would never clear `handlers.ts`'s module-scoped `let wishlist`. - Order matters: `beforeEach` runs after this file's `beforeAll`, so the server is already listening when the fixture is registered
- `localStorage.clear()` matters because two things persist to it: `cartStore`'s `persist` middleware and `ThemeProvider`'s `useLocalStorage("theme")`
- Adding MSW here changes **all five existing test files**, not just the new ones — see §7 step 6

### 6.6 `src/test/vitest-axe.d.ts` — NEW

`vitest-axe` documents `import "vitest-axe/extend-expect"` as the way to register its matcher. **That import does not compile in this project**, and the reason is worth understanding because it is the same mechanism v0.14 debugged with jest-dom.

The package's `dist/extend-expect.d.ts` declares:

```typescript
declare module "vitest" {
    interface Assertion extends AxeMatchers {}
}
```

Vitest 4 declares `interface Assertion<T>` — one type parameter, no default. Interface declaration merging requires **identical type parameters**, so merging a zero-parameter declaration with a one-parameter one fails:

```
error TS2428: All declarations of 'Assertion' must have identical type parameters.
```

`vitest.setup.ts` is inside the TypeScript program, so the augmentation *is* loaded and `pnpm exec tsc -b` fails. Splitting the import solves it: take the matcher from `vitest-axe/matchers` (which carries no `declare module`) and write the augmentation ourselves with the right shape.

```typescript
import type { AxeMatchers } from 'vitest-axe/matchers'

declare module 'vitest' {
  // eslint-disable-next-line @typescript-eslint/no-explicit-any
  interface Assertion<T = any> extends AxeMatchers {}
  interface AsymmetricMatchersContaining extends AxeMatchers {}
}
```

**Requirements:**
- **`Assertion<T = any>` — the `any` is load-bearing, not laziness.** `@testing-library/jest-dom/types/vitest.d.ts` is already in the program and declares `Assertion<T = any>`. Merged declarations must agree on the *default* as well as the arity: `<T>` + `<T = any>` compiles, and so does `<T>` + `<T = unknown>`, but `<T = any>` + `<T = unknown>` does not. Since jest-dom owns `any`, this file must use `any` too. Hence the targeted eslint-disable and the §9 carve-out
- `AsymmetricMatchersContaining` takes no type parameter — again matching jest-dom
- The top-level `import type` makes this a module, which is what turns `declare module 'vitest'` into an *augmentation* rather than a redeclaration
- Lives under `src/`, so `tsconfig.app.json`'s `include: ["src", ...]` already picks it up — no config change
- Verify with `pnpm exec tsc -b`. If TS2428 reappears, something has pulled `vitest-axe/extend-expect` back into the program; the fix is that import, not this file

### 6.8 `src/test/utils.tsx` — NEW

The shared render helper. It replaces the ad-hoc `renderWithClient` that v0.14 defined inside `ProductCard.test.tsx`.

```tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { render } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import type { ReactElement, ReactNode } from 'react'
import { Provider } from 'react-redux'
import { MemoryRouter } from 'react-router-dom'
import { AuthProvider } from '@/context/AuthProvider'
import { ThemeProvider } from '@/context/ThemeProvider'
import { makeStore } from '@/store'

interface RenderWithProvidersOptions {
  route?: string
}

export function renderWithProviders(
  ui: ReactElement,
  { route = '/' }: RenderWithProvidersOptions = {},
) {
  // A fresh client per render: no cache, no retries, no cross-test bleed.
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false },
      mutations: { retry: false },
    },
  })
  const store = makeStore()

  function Wrapper({ children }: { children: ReactNode }) {
    return (
      <QueryClientProvider client={queryClient}>
        <Provider store={store}>
          <MemoryRouter initialEntries={[route]}>
            <ThemeProvider>
              <AuthProvider>{children}</AuthProvider>
            </ThemeProvider>
          </MemoryRouter>
        </Provider>
      </QueryClientProvider>
    )
  }

  return {
    // Created before render(), as userEvent v14 requires.
    user: userEvent.setup(),
    queryClient,
    store,
    ...render(ui, { wrapper: Wrapper }),
  }
}
```

**Requirements:**
- Provider nesting **mirrors `src/main.tsx`** — `QueryClientProvider` → Redux `Provider` → Router → `ThemeProvider` → `AuthProvider`. Divergence here means tests exercise a tree the app never renders
- `MemoryRouter` replaces `BrowserRouter`: no real history, and `initialEntries={[route]}` is how a test lands on a deep route. `App.tsx` contains no router of its own, so `<App />` drops straight in
- `retry: false` on both queries and mutations — a retrying query turns a deliberate 500 into a multi-second timeout instead of an immediate error state
- Returning `user` removes one line of boilerplate from ~40 tests and guarantees `userEvent.setup()` runs *before* `render`, which is the ordering v14 requires
- `queryClient` and `store` are returned for the rare test that needs to inspect or seed them directly
- Returns everything RTL's `render` returns, so `container` is available for `axe`

```tsx
import { useEffect, useState } from 'react'
import { useNavigate } from 'react-router-dom'
import OrderConfirmation from '@/components/checkout/OrderConfirmation'
import PaymentForm from '@/components/checkout/PaymentForm'
import ShippingForm from '@/components/checkout/ShippingForm'
import { useCartStore } from '@/store/cartStore'
import type {
  CheckoutStep,
  OrderResult,
  PaymentData,
  ShippingData,
} from '@/types/checkout'

const STEPS: { key: CheckoutStep; label: string }[] = [
  { key: 'shipping', label: 'Shipping' },
  { key: 'payment', label: 'Payment' },
  { key: 'confirmation', label: 'Confirmation' },
]

export default function Checkout() {
  const [step, setStep] = useState<CheckoutStep>('shipping')
  const [shippingData, setShippingData] = useState<ShippingData | null>(null)
  const [orderResult, setOrderResult] = useState<OrderResult | null>(null)
  const [isSubmitting, setIsSubmitting] = useState(false)
  const [submitError, setSubmitError] = useState<string | null>(null)

  const items = useCartStore((state) => state.items)
  const navigate = useNavigate()

  useEffect(() => {
    if (items.length === 0) navigate('/cart', { replace: true })
  }, [items.length, navigate])

  const currentIndex = STEPS.findIndex((s) => s.key === step)

  function handleShippingSubmit(data: ShippingData) {
    setShippingData(data)
    setStep('payment')
  }

  async function handlePaymentSubmit(_paymentData: PaymentData) {
    setIsSubmitting(true)
    setSubmitError(null)
    try {
      const res = await fetch('/api/checkout', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ items, shipping: shippingData }),
      })
      if (!res.ok) throw new Error('Checkout failed')
      const result: OrderResult = await res.json()
      setOrderResult(result)
      setStep('confirmation')
    } catch {
      setSubmitError('Something went wrong. Please try again.')
    } finally {
      setIsSubmitting(false)
    }
  }

  function handleContinueShopping() {
    useCartStore.getState().clearCart()
    navigate('/')
  }

  return (
    <div className="max-w-xl mx-auto px-4 py-8">
      <h2 className="text-2xl font-bold text-gray-900 dark:text-white mb-6">
        Checkout
      </h2>

      <nav
        aria-label="Checkout steps"
        className="flex items-center gap-3 mb-8"
      >
        {STEPS.map(({ key, label }, index) => (
          <div key={key} className="flex items-center gap-3 flex-1 last:flex-none">
            <span className="flex items-center gap-2">
              <span
                className={
                  index <= currentIndex
                    ? 'w-2.5 h-2.5 rounded-full bg-blue-600'
                    : 'w-2.5 h-2.5 rounded-full bg-gray-300 dark:bg-gray-600'
                }
              />
              <span
                className={
                  index <= currentIndex
                    ? 'text-sm font-medium text-blue-600 dark:text-blue-400'
                    : 'text-sm text-gray-400 dark:text-gray-500'
                }
              >
                {label}
              </span>
            </span>
            {index < STEPS.length - 1 && (
              <span className="flex-1 h-px bg-gray-200 dark:bg-gray-700" />
            )}
          </div>
        ))}
      </nav>

      {step === 'shipping' && <ShippingForm onSubmit={handleShippingSubmit} />}

      {step === 'payment' && (
        <PaymentForm
          onSubmit={handlePaymentSubmit}
          isSubmitting={isSubmitting}
          error={submitError}
        />
      )}

      {step === 'confirmation' && orderResult && (
        <OrderConfirmation
          result={orderResult}
          onContinue={handleContinueShopping}
        />
      )}
    </div>
  )
}
```

**Requirements:**
- Import `useState`, `useEffect` from `react`; `useNavigate` from `react-router-dom`
- Import `useCartStore` from `@/store/cartStore`
- Import `CheckoutStep`, `ShippingData`, `PaymentData`, `OrderResult` from `@/types/checkout`
- Import the three children from `@/components/checkout/`
- **The fetch path is `/api/checkout`.** A bare `/checkout` matches no handler and, outside MSW, is not even a legal URL for Node's `fetch`
- **`clearCart()`, not `clear()`** — that is the action `cartStore` actually exposes
- `useCartStore.getState().clearCart()` is called imperatively inside the event handler — the correct Zustand pattern outside render
- `_paymentData` keeps its `_` prefix: the mock API receives only cart items and the shipping address, and `noUnusedParameters` is on, so the prefix is what makes it compile
- The `STEPS` array is module-level, so the indicator, the active-index maths, and the labels have one source. `currentIndex` is derived per render — no fourth piece of state

// `ProductCard` depends on `useWishlist()`, which needs a QueryClientProvider —
// and nothing else. The shared `renderWithProviders` would add four unused
// providers, so this file keeps its own one-line helper.
function renderWithClient(component: React.ReactElement) {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false },
    },
  })

  return render(
    <QueryClientProvider client={queryClient}>{component}</QueryClientProvider>,
  )
}

    expect(
      await screen.findByRole('button', { name: /add to wishlist/i }),
    ).toBeInTheDocument()
  })

  it('labels the heart "Remove from wishlist" when the fetched wishlist contains the product', async () => {
    server.use(...wishlistHandlers(['1']))
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />)

    expect(
      await screen.findByRole('button', { name: /remove from wishlist/i }),
    ).toBeInTheDocument()
  })

  it('optimistically marks the product as wishlisted before the request settles', async () => {
    const user = userEvent.setup()
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />)

    await user.click(
      await screen.findByRole('button', { name: /add to wishlist/i }),
    )

    // The POST is held open by the fixture's delay(300), so the label written
    // by `onMutate` is observable before the server has answered.
    expect(
      await screen.findByRole('button', { name: /remove from wishlist/i }),
    ).toBeInTheDocument()
  })

  it('rolls the label back when the add request fails', async () => {
    server.use(
      http.post('/api/wishlist/:productId', async () => {
        await delay(300)
        return new HttpResponse(null, { status: 500 })
      }),
    )
    const user = userEvent.setup()
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />)

    await user.click(
      await screen.findByRole('button', { name: /add to wishlist/i }),
    )

    // Await the optimistic state first. Without this the final assertion would
    // match the *initial* label and pass whether or not onError ever ran.
    await screen.findByRole('button', { name: /remove from wishlist/i })

    expect(
      await screen.findByRole('button', { name: /add to wishlist/i }),
    ).toBeInTheDocument()
  })

  it("keeps the server's wishlist after the mutation settles", async () => {
    // The label alone cannot distinguish "optimistic update held" from
    // "refetched and confirmed" — both read "Remove from wishlist". Counting the
    // GET is what actually proves onSettled invalidated and refetched.
    let wishlist: string[] = []
    let getCount = 0

    server.use(
      // No delay on GET — deliberately, and only here. This test waits on two
      // round-trips (POST, then the onSettled refetch); at the fixture's uniform
      // delay(300) that is ~900 ms against waitFor's 1000 ms default. §6.4 keeps
      // the shared fixture faithful and sanctions exactly this kind of per-test
      // override when a window needs widening.
      http.get('/api/wishlist', () => {
        getCount += 1
        return HttpResponse.json(wishlist)
      }),
      http.post('/api/wishlist/:productId', async ({ params }) => {
        await delay(300)
        wishlist = [...wishlist, params.productId as string]
        return HttpResponse.json({ id: params.productId })
      }),
    )

    const user = userEvent.setup()
    renderWithClient(<ProductCard product={mockProduct} variant="compact" />)

    await user.click(
      await screen.findByRole('button', { name: /add to wishlist/i }),
    )

    await waitFor(() => expect(getCount).toBeGreaterThan(1))

    expect(wishlist).toEqual(['1'])
    expect(
      screen.getByRole('button', { name: /remove from wishlist/i }),
    ).toBeInTheDocument()
  })
})

## 8. Concepts Learned

| Concept | Where it appears | Why it matters |
| --- | --- | --- |
| Integration test vs unit test | `checkout.integration.test.tsx` | Integration tests render a real component tree and simulate a full journey across components, routing, and async state; unit tests isolate one unit. Different failure surfaces, both necessary |
| MSW `setupServer` in Node | `src/mocks/server.ts` | Intercepts `fetch` at the request layer, so components run their real network code. It also **resolves relative URLs** — a bare `fetch("/api/checkout")` throws `Failed to parse URL` under plain undici, but MSW resolves it against `location` before the request is constructed |
| Numeric vs argless MSW `delay` | `POST /api/checkout` | `delay(300)` waits the full 300 ms *in tests too* — it is not shortened. Argless `delay()` asks for a "realistic" duration, which MSW resolves to **5 ms under Node** and 100–400 ms in a browser. Argless is almost always what a handler wants |
| A shared render helper | `src/test/utils.tsx` | One place that mirrors the app's provider tree. When a test renders under a different tree than production, it proves something about a tree that does not exist |
| Store factories in tests | `makeStore()` | A module-level singleton is shared by every test in a process. Factories are how each test gets a clean slate — the Redux counterpart to `useCartStore.setState({ items: [] })` |
| Green for the wrong reason | Empty-cart guard test | A synchronous assertion against a lazy route passes while the Suspense fallback is up, guard or no guard. Whenever a test "passes", ask what would have to break for it to fail |
| `findBy*` vs `getBy*` for async UI | After render and step transitions | `getBy*` throws immediately if the element is absent; `findBy*` returns a promise and polls (1 s default) — required whenever Suspense or a request stands between render and content |
| `waitFor` for a batch of changes | Validation-error assertions | Retries a whole block until it passes. Right when several messages must appear together; a single `findBy*` is better for one element |
| `screen.getByLabelText` | Every form field query | Queries the field *and* proves the `htmlFor`/`id` pairing exists. A missing label fails the test before axe ever runs |
| `user.tab()` fires `onBlur` | Postal code and card number tests | Tab moves focus away, firing `blur` — the event RHF's `mode: 'onBlur'` listens for. Inline-error tests must blur first |
| `server.use(...)` prepends | 500 tests, rollback test, the wishlist fixture | Runtime handlers go in front of the base set and MSW takes the first match, so the most recent `use()` wins. That single rule covers both jobs: a global `beforeEach` can shadow a route for the whole suite, and a test can still override that shadow |
| Test fixtures over reset functions | `wishlistHandlers()` vs `resetWishlist()` | `resetHandlers()` restores handler *functions*, never their closure state — so a module-scoped `let` in a mock needs *something*. Exporting a reset from the mock keeps the singleton and adds a test-only export to the module the dev browser loads; a factory deletes the shared state instead. Same move as `makeStore()`, one layer down |
| axe scans a subtree, not a page | Three axe test cases | Page-level rules (`page-has-heading-one`, `landmark-one-main`, `html-has-lang`, `bypass`) select `html:not(html *)`, which cannot match inside RTL's `container` — so they never fire. `region` selects `body *` and does apply; it passes because all content lives in `<header>`/`<main>`. Scanning `container` is narrower than a real page audit, and knowing *which* rules you skipped is the difference between a green test and a green claim |
| Matcher type augmentation must match arity | `src/test/vitest-axe.d.ts` | `expect.extend` is runtime; making TypeScript aware needs `declare module "vitest"`. Merged declarations must agree on type parameters *and defaults* — `<T>` + `<T = any>` compiles, `<T = any>` + `<T = unknown>` does not. A package whose augmentation predates your test runner will fail with TS2428, and the fix is to import the matcher without the augmentation and write your own |
| V8 coverage | `pnpm test:coverage` | The V8 provider reads the engine's own counters instead of instrumenting source, so it is fast and needs no Babel step. Excluding tests, mocks, and helpers keeps the number about product code |
| RHF `mode: 'onBlur'` | Both forms | Defers validation until focus leaves a field, so errors do not flash mid-typing. In tests, `user.tab()` is how you trigger it |
| Cart guard with `useEffect` + `navigate` | `Checkout.tsx` | A reactive condition plus `navigate(..., { replace: true })` is the React Router route-guard pattern; `replace` keeps the guarded route out of history so Back does not bounce |

## 9. Acceptance Criteria

The module is complete when all of the following pass.

**Build and types**

- [ ] `pnpm exec tsc -b` exits with zero errors. **Not `tsc --noEmit`** — the root `tsconfig.json` is a solution file (`"files": []` + references), so `--noEmit` type-checks **zero** files and passes unconditionally. `tsc -b` checks all 49

- [ ] No `any` types in new or modified files, except the single documented `Assertion<T = any>` in `src/test/vitest-axe.d.ts`, which must match jest-dom's default to merge
- [ ] Cross-file imports in new and modified files use the `@/` alias. Same-directory imports (`./handlers`) stay relative
