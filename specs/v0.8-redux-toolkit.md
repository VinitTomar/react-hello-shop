# v0.8 — Redux Toolkit

### Product Requirement Specification

---

## 1. Overview

**Goal:** Add user profile and order history state to ReactMart using Redux Toolkit. Create two RTK slices (`userSlice`, `ordersSlice`), each with a `createAsyncThunk` that simulates an API fetch with a brief delay. Wire the slices into a `configureStore` instance and expose typed `useAppSelector`/`useAppDispatch` hooks. Add two new pages — `/profile` and `/orders` — and link to them from the Header.

**End result:** Visiting `/profile` shows a 600 ms loading skeleton, then the mock user's avatar, name, email, and join date. Visiting `/orders` shows an 800 ms loading skeleton, then a list of three mock orders with status badges, item counts, and totals. Navigating away and back skips the re-fetch because the slice's `status` is already `'succeeded'`. Redux DevTools shows both slices and lets you time-travel to before the fulfilled actions. Cart state remains in Zustand — the two stores coexist without interference.

**Why this comes after v0.7:** v0.7 introduces Context for lightweight, infrequently-changing UI state (auth identity, theme preference). v0.8 introduces RTK for heavier async state that benefits from formal loading/error tracking and DevTools introspection. Seeing both in the same app is the clearest demonstration of when to reach for each tool.

### Module Constraints

- **No real API.** Profile and orders are returned from private mock constants inside each slice file. A `setTimeout` delay simulates network latency.
- **Cart stays in Zustand.** The cart is not migrated to RTK. This coexistence is intentional — it demonstrates the right tool for each job.
- **No auth gating.** `/profile` and `/orders` are publicly accessible in v0.8. Auth-gated routes are a v0.7 concern; v0.8 assumes the user is always "logged in" via the mock profile.
- **No order placement.** Orders are read-only. The checkout flow is v0.15.
- **Tailwind only.** No inline styles, no CSS modules.
- **React 19 JSX transform.** `import React from 'react'` is not needed.

## 4. Type Definitions

Defined and exported from `src/types/user.ts`.

```ts
export interface UserProfile {
  id: string;
  name: string;
  email: string;
  avatarUrl: string;
  joinedAt: string; // ISO date string: 'YYYY-MM-DD'
}

export type OrderStatus = 'processing' | 'shipped' | 'delivered';

export interface OrderItem {
  product: Product;
  quantity: number;
  unitPrice: number; // snapshot of price at order time — may differ from current product price
}

export interface Order {
  id: string;
  createdAt: string; // ISO date string: 'YYYY-MM-DD'
  status: OrderStatus;
  items: OrderItem[];
  total: number;
}
```

RTK slice-internal state shapes (defined in each slice file, not re-exported):

```ts
// userSlice.ts
interface UserState {
  profile: UserProfile | null;
  status: 'idle' | 'loading' | 'succeeded' | 'failed';
  error: string | null;
}

// ordersSlice.ts
interface OrdersState {
  orders: Order[];
  status: 'idle' | 'loading' | 'succeeded' | 'failed';
  error: string | null;
}
```

**Design notes:**
- `unitPrice` in `OrderItem` is a snapshot, not a live reference. For mock data, it can equal `product.price`, but the type enforces the snapshot pattern that matters when real prices change.
- `status` follows the RTK-recommended four-state enum pattern — components switch on it to render idle, loading, data, or error UI.
- `UserProfile` is separate from `AuthContext`'s `User` type (v0.7). `User` is an auth identity (id, email, name). `UserProfile` is richer display data (avatar, joinedAt). They could be merged in v0.9 when a real API returns them together.

### 6.2 `src/store/index.ts` — NEW

**Requirements:**
- Install: `pnpm add @reduxjs/toolkit react-redux`
- Import `configureStore` from `@reduxjs/toolkit`
- Import `useDispatch`, `useSelector` from `react-redux`
- Import `userReducer` from `./userSlice`
- Import `ordersReducer` from `./ordersSlice`

```ts
import { configureStore } from '@reduxjs/toolkit'
import { useDispatch, useSelector } from 'react-redux'
import userReducer from '@/store/userSlice'
import ordersReducer from '@/store/ordersSlice'

export const store = configureStore({
  reducer: {
    user: userReducer,
    orders: ordersReducer,
  },
})

export type RootState = ReturnType<typeof store.getState>
export type AppDispatch = typeof store.dispatch

export const useAppDispatch = useDispatch.withTypes<AppDispatch>()
export const useAppSelector = useSelector.withTypes<RootState>()
```

**Notes:**
- `configureStore` automatically enables Redux DevTools in development, configures `redux-thunk`, and wraps reducers with Immer — no manual middleware setup needed.
- `RootState` is derived from the store (not hand-written) so it always stays in sync as new slices are added.
- `withTypes` (RTK 2.0+) binds the type to the hook so components never need to write `useSelector<RootState>()` or `useDispatch<AppDispatch>()` by hand.

### 6.3 `src/store/userSlice.ts` — NEW

**Mock data (private — not exported):**

```ts
const MOCK_PROFILE: UserProfile = {
  id: 'user-1',
  name: 'Alex Johnson',
  email: 'alex@example.com',
  avatarUrl: 'https://picsum.photos/seed/user1/200/200',
  joinedAt: '2024-01-15',
}
```

**Thunk:**

```ts
export const fetchProfile = createAsyncThunk<UserProfile>(
  'user/fetchProfile',
  async () => {
    await new Promise<void>((resolve) => setTimeout(resolve, 600));
    return MOCK_PROFILE;
  }
);
```

**State interface (internal):**

```ts
interface UserState {
  profile: UserProfile | null;
  status: 'idle' | 'loading' | 'succeeded' | 'failed';
  error: string | null;
}
```

**Slice:**

```ts
const userSlice = createSlice({
  name: 'user',
  initialState: {
    profile: null,
    status: 'idle',
    error: null,
  } as UserState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchProfile.pending, (state) => {
        state.status = 'loading';
      })
      .addCase(fetchProfile.fulfilled, (state, action) => {
        state.status = 'succeeded';
        state.profile = action.payload;
      })
      .addCase(fetchProfile.rejected, (state, action) => {
        state.status = 'failed';
        state.error = action.error.message ?? 'Failed to load profile';
      });
  },
});

export default userSlice.reducer;
```

**Requirements:**
- Import `createAsyncThunk`, `createSlice` from `@reduxjs/toolkit`
- Import `UserProfile` from `@/types/user`
- No synchronous reducers needed — `reducers: {}` is intentional
- The `as UserState` cast on `initialState` is required because TypeScript cannot narrow `null` to `UserProfile | null` without it

## 8. Concepts Learned

| Concept | Where it appears | Why it matters |
| --- | --- | --- |
| `configureStore` | `store/index.ts` | Replaces Redux's `createStore`; auto-enables DevTools, Immer, and `redux-thunk` — no manual middleware setup needed |
| `RootState` and `AppDispatch` | `store/index.ts` | Derived from the store so they stay accurate as slices are added or removed; the two types every RTK file needs |
| Typed hooks (`withTypes`) | `store/index.ts` | `useAppSelector` and `useAppDispatch` carry full type information; components get inference without repeating generics |
| `createSlice` | `userSlice.ts`, `ordersSlice.ts` | Co-locates action creators + reducer in one call; Immer lets you write `state.profile = action.payload` directly instead of returning a new object |
| `createAsyncThunk` | `userSlice.ts`, `ordersSlice.ts` | Generates `pending` / `fulfilled` / `rejected` action types automatically; handles the promise lifecycle so the slice only needs to handle state transitions |
| `extraReducers` + `builder.addCase` | Both slices | The bridge between a thunk's lifecycle and a slice's state; `builder` pattern gives full type inference on `action.payload` |
| Four-state status pattern | Both slices | `'idle' \| 'loading' \| 'succeeded' \| 'failed'` is RTK's idiomatic way to represent async state — components switch on it for conditional rendering |
| `useAppSelector` | `Profile.tsx`, `Orders.tsx` | Subscribes a component to a slice of state; re-renders only when that slice changes (not on every store update) |
| RTK vs Zustand | Cart (Zustand) vs Profile/Orders (RTK) | RTK fits: async state, formal loading/error lifecycle, DevTools-heavy debugging, team-scale projects. Zustand fits: synchronous client state, low boilerplate, simple shapes |
